# 基础数据引用与接口幂等盘点

盘点范围：`backend/app/api/v1` 全部写接口 + `app/modules/*/services.py` 服务层 + `alembic/versions` 唯一约束。只做盘点，本轮不改代码。

结论先行：

1. **除费用发票外，业务写接口对产品、客户、供应商、合作伙伴没有任何服务端存在性或启用状态校验。** 全后端搜索 `from app.modules.masterdata`，只有 `system/printing`、`purchase/contracts`、`finance/fee_payments`、`finance/overview` 四处引用主数据。
2. **仓库、库位根本不是主数据。** 没有 `warehouses`/`locations` 表，单据里的 `warehouse_id`/`warehouse_name`/`location_id`/`location_name` 都是前端传的文本（前端还写死了 `wh-company`/`公司仓库`）。这一项无法做存在性校验，只能先决定要不要建表。
3. **生成型接口只有 3 处有数据库唯一约束兜底**（采购合同→入库计划、采购合同→跟单计划、样品费用汇总），其余重复请求要么新建第二份，要么只靠「先查再插」的业务判断，并发下仍会重复。
4. **快照口径是混合的。** 所有列表、详情、报表、导出用写入时快照；只有打印模板会实时回读客户主联系人、供应商地址/联系人、产品图片/包装。同一份采购合同可能出现「旧供应商名 + 新地址」。

### 1.2 分档结论

**A. 完全没有服务端校验（新增主数据引用只靠前端下拉）**

- 销售：报价创建/修改、出口合同创建/修改
- 采购：询价创建/修改、供应商报价行、采购合同创建/修改
- 样品：申请、样品登记、导入、寄样
- 仓库：入库计划、入库单、出库计划、出库单（供应商、客户、产品、仓库、库位全不校验）
- 财务：收款、供应商发票、付款申请、杂费、核销单客户、口岸数据
- 主数据：单证资料的 `customer_id`

**B. 只校验了上游单据，没有校验主数据**

- 出货单：只校验出口合同
- 入库计划：只校验采购合同
- 入库单/出库单：只校验计划
- 出库计划：只校验出货单
- QC、跟单计划：只校验采购合同
- 结算：只校验出运单
- 核销单：只校验出运单（且允许不填）

**C. 真正做了主数据校验**

| 接口 | 校验内容 | 不足 |
|---|---|---|
| 费用发票、付费申请 | 合作伙伴存在、名称一致、类型一致、active | 只有填了 `partner_id` 才校验；表单是手填 ID |
| 出口合同生成采购合同 | 产品存在（按 ID 或编码），配件能查到 | 不校验产品停用；供应商完全不校验 |
| 员工选择（审核人、QC 检验员） | 用户存在且启用（`AssigneeValidator`） | 只覆盖审核/检验角色，销售员、认领人、申请人仍直接落 payload |

### 2.2 分档结论

- **必然重复新建**：出口合同→采购合同、报关单→开票通知、计划→入库/出库单、合同→出货单、样品费用→付款申请。
- **串行能挡、并发挡不住**：报价→合同、出货单→出库计划、申请→样品登记、出运单→结算、核销单→退税。
- **已有数据库兜底**：采购合同→入库计划、采购合同→跟单计划。
- **允许分批、不能用 source 唯一**：出货单、入库单、出库单。这三类必须引入「请求幂等键」或客户端幂等 token，不能简单给 `source_id` 加唯一。

## 三、快照口径

### 3.1 打印 / 导出

### 3.2 详情 / 列表 / 报表

| 读取点 | 口径 | 说明 |

| 出口合同、报价、采购合同、出货、QC、出入库详情 | 纯快照 | 服务层没有引用主数据仓储，名称/规格/地址全部读单据字段 |

### 3.3 混合口径清单（同一份单据上信息来自不同时点）

2. 采购合同打印：供应商名称 = 签约时快照；供应商地址、电话、邮箱 = 打印时实时。

4. 财务总览：伙伴数量按当前主数据统计；费用金额按单据快照统计。

## 四、建议分批范围

### 第一批：服务端校验 + 下拉改服务端搜索

**服务层统一校验**

- 新建共享校验器（例如 `modules/masterdata/validators.py`），提供 `require_product/require_customer/require_supplier/require_partner/require_document_party`，返回主数据行并检查 `status=active`。
- 校验口径：**新建与修改时，只要提交了新的主数据 ID 就必须存在且启用；编辑旧单据保留原 ID 时不因后来停用而报错。**
- 覆盖：销售报价/合同、采购询价/合同/开票通知、样品申请/登记/寄样、入库/出库计划与单据、收款/付款/费用/杂费/核销、单证资料。
- `customer_name`/`supplier_name`/`product_name` 一律由服务端按 ID 回填，忽略前端传值，避免「ID 指向 A、名称写 B」。
- 费用发票去掉「不填 partner_id 也能建」的口子，改为主数据选择。
- 仓库/库位：先确认是否建主数据表；未建表之前，服务端至少校验 `warehouse_id`/`location_id` 非空且成对出现，并在文档里标注为临时方案。

**下拉**

- 四个一次性加载点改成带 `q` 的服务端搜索（防抖 300ms、最少 1 个字符、返回 20 条）。
- 所有选择器显式传 `status=active`；后端 `list_customers`/`list_suppliers`/`list_partners` 增加 `active_only` 默认值，避免停用记录进入下拉。
- 费用发票的 `partner_id` 改为可搜索选择。

**测试**：不存在 ID、已停用 ID、名称与 ID 不一致、编辑旧单据保留停用 ID。

### 第二批：生成型接口幂等

- **加唯一约束**：
  - `export_contracts.source_quotation_id` 部分唯一（非空时唯一）。
  - 采购合同来源关联：`source_export_contract_line_id` 部分唯一（排除已取消采购合同）。
  - `outbound_plans(source_type, source_id)` 唯一。
  - `settlements.shipment_plan_id` 唯一。
  - `purchase_invoice_notices(customs_declaration_id, supplier_id)` 唯一。
  - 样品登记 `(source_type, source_id)` 部分唯一。
  - 样品费用 → 付款申请：费用行增加 `payment_request_id` 唯一，生成前判断。
- **允许分批的三类**（出货单、入库单、出库单）：新增 `request_key`（客户端每次提交生成 UUID，服务端唯一），重复请求返回首次结果。
- **并发处理**：捕获 `IntegrityError`，生成型返回既有单据，追加型返回 409 并提示重复。
- **事务**：生成动作整体放进一个 `UnitOfWork`；当前「先查再插」的业务判断保留，但只作为友好提示，不作为并发防线。
- **测试**：顺序重复、并发重复（两个协程/两个连接）、唯一约束冲突后的返回结果。

### 第三批：统一快照口径

建议**统一为写入时快照**，理由：单据要可重现，打印不能随主数据变化。具体：

- 合同表补充快照列：客户地址、客户主联系人姓名/电话/邮箱；供应商地址、主联系人姓名/电话/邮箱。
- 合同行补充：产品包装说明、产品图片 URL（生成时写入）。
- 打印模板改为只读单据快照，不再调用 `get_customer`/`get_supplier`/`get_product`。
- 历史数据迁移：新增列先允许为空，回填一次当前主数据值，之后写入时固化。
- 财务总览的伙伴类型统计属于分析口径，可以保留实时，但需在页面标注「按当前主数据统计」。

## 五、需要确认的决策点

1. **仓库/库位是否建主数据表？** 当前没有表，无法做存在性校验，只能先做文本校验。
2. **单证资料是否接入出口合同/出货？** 当前完全没有下游引用，若不接入，第一批不需要为它加校验。
3. **出货单、入库单、出库单是否允许分批？** 允许则用幂等键，不允许则直接给 `source_id` 加唯一约束。
4. **快照方向是否按「写入时快照」统一？** 这会改变现有打印结果：历史合同补快照前，打印将不再显示最新地址/联系人。
5. **历史数据如何处理？** 新增快照列需要一次性回填；不回填则旧单据打印为空。
