## 一、结论先行

前端的问题不是「所有地方都失控」，而是**三套生产模式没有收敛，叠加三类历史遗留**：

1. **页面生产模式未收敛**：28 个业务页面中，财务模块已经按 `FinancePage + hooks + views` 分层，其余页面仍是单文件里同时放列表、筛选、表单、弹窗、提交反馈；表单体系是手写受控状态（0 处 `Form.Item`、90 处 `FormSelect`），每个弹窗各自维护 `open/submitting/error`。
2. **样式存在两套全局层**：`styles.css` 顺序引入 15 个分片，`design-system.css`（1316 行、44 处 `!important`）却在 `main.tsx` 中最后加载，形成「分片 → 设计系统覆盖」的反向层叠；`.ant-table` 等选择器分散在 4–11 个文件中重复覆盖。
3. **页面状态没有进入 URL**：列表页筛选、搜索、选中项全部使用本地 `useState`，没有页面使用 URL 查询参数；刷新、后退、分享链接都会丢状态。这与当前手写 history 路由直接相关。

同时有 **4 个比「乱」更值得优先修的正确性问题**：

| 编号 | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| P0-1 | 语言/时区切换未接入运行时格式化 | `appHelpers.tsx:90-98` 的 `setRuntimeSettings` 从未被调用；`appI18n.ts:270-272` 的 `t()` 默认 zh-CN；页面 173 处 `t()`、43 处 `formatDate()` 全部不传 settings | 切到 English 只改变 antd 组件语言，页面文案和日期仍按中文/UTC+8；若后端配置 UTC，日期展示错误 |
| P0-2 | 设置弹窗「保存头像」是空操作 | `App.tsx:45` 的 `savingSettingsAvatar` 无 setter 恒为 false，`App.tsx:253` `onSaveAvatar: () => {}`；`SettingsModal.tsx:47` 按钮可点击 | 用户修改头像后点击保存没有任何效果，是可见的坏功能 |
| P0-3 | 列表没有分页，超出默认条数的数据不可见 | 92/93 处表格 `pagination={false}`，0 处 `<Pagination>`；前端列表 API 不传 `limit/offset`（如 `api/warehouse.ts:437`），后端默认 50 条封顶 | 数据超过 50 条后，旧记录无法在界面访问，属于功能缺口而非风格问题 |
| P0-4 | 死代码与断链命令 | `src/legacy/App.vue` 13681 行且无引用；`scripts/` 只有 `.gitkeep`，但 `package.json:11-14` 有 4 个 e2e/test 脚本指向不存在的文件 | 误导后续开发，`npm run test:all` 等命令直接失败 |

**做得好的部分（应保留，不要在这次整理中推翻）**：

- 请求层统一：除登录外全部走 `api/core.ts` 的 `request()`；`api.ts` 是 63 行纯 re-export 出口，页面没有绕过。
- 错误提示统一：页面层 156 处 `showError()`，没有 `message.error()` 直接调用。
- 类型统一：主业务实体类型集中在 `src/api/*`，页面没有重复定义，TS/TSX 中 0 处 `any`。
- 复用已有成功案例：`TradingPartnerPage` 一套实现服务客户/供应商/合作伙伴三个 60 行入口；`shared/ui` 通过 barrel 使用 35 处，`FormSelect` 90 处。
- 财务模块的拆分范式（`FinancePage.tsx` 322 行 + `hooks/` + `views/`）是后续拆大页面的现成模板。

#### A-4【部分解决】新增一个页面仍要登记两处：页面注册表 + 后端菜单

- **状态**：部分解决（`d2daa63`、`a62a331`、`2515056`）。路径已由 `routes.ts` 的 `routeDefinitions` / `routeRegistry` 统一；`AppRouter` 已改为由 `pageRegistry.tsx` 解析渲染，不再逐条 `activePath === xxxPath` 分支；前后端路径一致性已有契约测试。仍未收敛的是：
  1. **菜单元数据前后端双存（暂不收敛）**：后端 `seed_navigation.py` 保存菜单标题/英文名/图标/权限/排序/路径，是「菜单是否存在、谁能看到、如何排序」的事实来源；前端 `routeDefinitions` 保存 `titleKey`/`navGroup`/`navChild`/`detailRoot`，是「分到哪个分组、分组图标、语言切换标题兜底」的事实来源。路径是共享契约，已由测试守住；标题/图标/权限/排序仍各存一份。
  2. **页面组件与 props 仍需登记**：新增页面要在 `pageRegistry.tsx` 增加一个 `RouteKey -> 渲染函数` 条目，并保持 `React.lazy` 静态 import 映射；这是懒加载的固有成本，已从「分支链」变为「表项」。
- **风险**：后端新增菜单若前端没有对应路由，契约测试会失败并列出路径；若只加菜单没加 `navGroup`，菜单会落到「其他」分组；标题/图标/排序改了一侧而另一侧未同步，不会报错，只会显示旧文案或旧顺序。
- **改法（后续，非本轮）**：若要彻底收敛，需要给菜单表加 `group` 字段 + 迁移 + 种子数据 + 前端改为纯后端驱动，并把 `core/i18n_config.py` 的 `sidebar_groups` 删除或标注废弃；属于跨库表与渲染的联动改造，收益低于成本，建议新增一级业务域时再做。

#### A-5【可以接受】目录粒度与命名不统一，但未造成实际混乱

- 证据：`app/components/` 下 `router/`、`settings/`、`shell/`、`sidebar/`、`topbar/` 多数只有 1 个文件；`shared/ui/` 是扁平结构；页面测试集中在 `pages/__tests__/`，但 `AppSidebar.test.tsx` 与组件同目录。
- 影响：主要是「看起来不统一」，当前引用关系清晰。
- 是否值得改：暂不值得为目录而搬迁；在 `docs/` 记录约定，后续新增代码遵守即可。
- 约定建议：页面私有组件放页面目录，跨页面组件进 `shared/ui`，页面级测试统一进 `pages/__tests__/`。

#### A-6【可以接受】`design-system.css` 放在 `src` 根目录

## 五、明确不建议做的事

1. **不要一次性引入 react-router 重写路由**：当前问题不是缺路由库，而是 URL 状态和注册表；先用现有 history 路由解决 query 与注册表。
2. **不要把所有页面塞进一个通用 CRUD 框架**：只抽 `ListPageShell`、`FormModal`、`useSubmitAction` 三个薄模式，业务字段和校验留在页面。
3. **不要在未建立视觉基线时大改 CSS**：样式阶段必须先截图、再按选择器族小步删改。
4. **不要把 Semi 迁移、样式收敛、页面拆分混在一个提交**：三者风险类型不同，回退粒度会失效。
5. **不要为了行数机械拆文件**：只拆职责边界清晰的页面；`TradingPartnerPage` 这类高复用抽象保留。
