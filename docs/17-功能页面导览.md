# 功能页面导览

> 本文档用于逐页向用户讲解系统功能。第一批只做「全景清单」，逐页展开（用途、使用角色、列表列、表单字段、动作与状态流转、接口与表、已知局限）在清单确认后另起章节。
>
> 口径：以 `frontend/src/app/routes.ts` 的 `routeDefinitions` 为唯一路由依据；权限码取后端种子菜单 `backend/app/modules/system/auth/seed_navigation.py` 的 `required_permission`；菜单顺序取该文件的 `sort_order`，分组取 `frontend/src/app/routes.ts` 的 `navGroup` 与 `frontend/src/app/components/sidebar/sidebarNavigation.ts` 的分组顺序。状态结论来自对页面组件、页面注册表和实际操作入口的核对。

## 0. 核对结论摘要

- `routeDefinitions` 共 **41 条**路由；`pageRegistry` 有 **41 个**渲染器，**没有缺失渲染器的路由**。
- 后端种子菜单共 **37 条**菜单路径，全部能命中 `routeDefinitions`；剩余 **4 条**为工作台子页，不在侧边栏。
- 41 条路由中：完整可用 **35** 条；只有列表无详情 **1** 条；只读展示 **5** 条；空壳 **0** 条；整页级「有接口无入口」**0** 条。
- 所有带 `detailRoot` 的页面，详情路径都由根路径派生，不在 `routeDefinitions` 中单独注册；下文在「路由」列以 `{id}` 标出。

## 3. 代码里存在但用户看不到的页面

结论：**`routeDefinitions` 内没有完全无入口的页面。** 具体边界如下：

1. **不在侧边栏、但有站内入口的 4 个工作台子页**：待办、日程、通知、公告。
   - 工作台卡片/面板可跳转：`dashboard/DashboardPage.tsx:356-375`、`dashboard/views/DashboardOverviewPanels.tsx:63-278`。
   - 通知另有顶栏铃铛入口（`frontend/src/app/components/topbar/NotificationBell.tsx`）。
2. **不在 `routeDefinitions` 的两个状态页**（不属于业务菜单，但用户会看到）：
   - 登录页 `/login`：`frontend/src/app/pages/auth/LoginPage.tsx`，由 `frontend/src/app/App.tsx:258` 在未登录时渲染。
   - 无权限页 `AccessDeniedPage`：由 `frontend/src/app/components/router/AppRouter.tsx:7-9,38-55` 在无权访问时渲染，组件位于 `reporting/ReportingPage.tsx`。
3. **共用基座组件不是独立页面**：`masterdata/TradingPartnerPage.tsx` 被客户、工厂、合作伙伴三个页面复用，没有自己的路由。
4. **未发现孤儿页面**：所有 `pages/**/*Page.tsx` 要么在 `pageRegistry` 中注册，要么是上述共用基座/登录页；没有「组件存在但既无菜单也无站内跳转」的业务页面。

## 4. 菜单里有但点进去是空壳的页面

结论：**本轮核对为 0 个。**

依据：后端种子菜单 37 条路径全部命中 `routeDefinitions`；`routeDefinitions` 的 41 条路由全部命中 `pageRegistry` 的页面渲染器（41/41）；页面代码中没有「开发中」「敬请期待」「暂未开放」等占位文案。

但以下 5 个页面是**轻量或只读视图**，容易被误认为空壳，讲解时需要提前说明：

| 页面 | 实际内容 | 为什么容易被误判 |
|---|---|---|
| 25 财务摘要 `/finance` | 关键金额摘要 + 财务模块导航卡片 | 没有列表和表单，看起来像入口页 |
| 26 经营总览 `/finance/overview` | 经营指标汇总与趋势 | 纯展示，无写操作 |
| 35 财务报表 `/finance/reports` | 多类报表、筛选、下钻、CSV 导出 | 只有查询与导出 |
| 36 老板看板 `/reporting` | 审批聚合、统计与跳转处理 | 只有聚合查询 |
| 5 公告 `/workspace/announcements` | 已发布公告只读列表 | 无新增/编辑入口（发布在工作台） |

## 5. 命名与入口注意事项

## 第一章 基础资料

### 1.0 先统一两个口径

- 菜单「**工厂资料**」就是**供应商**（`/masterdata/suppliers`，表 `suppliers`）。系统里没有独立的「工厂」实体，工厂、外发加工厂都按供应商登记。
- 菜单「**订单中心**」就是**出口合同**（`/sales/contracts`，表 `export_contracts`），不是所有订单的总入口。采购合同在另一页。
- 本章及后续章节统一称「供应商」「出口合同」。

### 1.1 五类主数据一览

| 主数据 | 页面 | 主表 | 下游怎么引用 | 删除方式 |
|---|---|---|---|---|
| 产品 | 产品资料 | `products` + `product_accessories` | 逻辑 ID + 产品编码/名称/规格/型号/单位快照 | 软停用；配件物理删除 |
| 供应商 | 工厂资料 | `suppliers` + 联系人 + 信用档案 | 逻辑 ID + 供应商名称快照 | 软停用；联系人物理删除 |
| 客户 | 客户资料 | `customers` + 联系人 + 信用档案 | 逻辑 ID + 客户名称快照 | 软停用；联系人物理删除 |
| 合作伙伴 | 合作伙伴 | `partners` + 联系人 | 逻辑 ID + 伙伴名称/类型快照 | 软停用；联系人物理删除 |
| 单证资料 | 单证资料 | `document_parties` | **没有任何下游引用** | 软停用；停用时清默认标记 |

### 1.2 贯穿全章的共性结论

这五类主数据在系统里的接入方式是统一的，先讲共性，后面每类只讲差异。

1. **主数据内部是真外键，业务单据不是。** 联系人、信用档案、产品配件都通过数据库外键挂在主表上（`backend/app/modules/masterdata/customers/models.py:38`、`suppliers/models.py:38`、`partners/models.py:38`、`products/models.py:48`）。但报价行、合同行、出货行、出入库单、付款单引用主数据时，全部是普通 `String(36)` 字段加名称快照，没有数据库外键。数据库层不会阻止写入一个不存在的主数据 ID。
2. **后端创建单据时基本不校验主数据。** 出口报价、出口合同、采购合同、收款、付款、出货等接口，直接把前端传来的 `customer_id`/`customer_name`/`supplier_id`/`supplier_name` 落库（例如 `sales/contracts/services.py:83-99`、`purchase/contracts/services.py:107-108`、`finance/receipts/models.py:22-23`）。是否存在、是否停用，不校验。只有三处例外：费用发票创建时会校验合作伙伴名称/类型/状态（1.6）、从出口合同生成采购合同时会按产品 ID 或编码回查产品与配件（1.3）、打印/导出会实时回读主数据（下一条）。
3. **删除一律是软停用。** 五个 `DELETE` 端点都只把 `status` 改为 `inactive`，没有任何引用检查，也不联动停用下游（`products/services.py:161-177`、`customers/services.py:270-292`、`suppliers/services.py:266-288`、`partners/services.py:246-265`、`document_parties/services.py:185-200`）。联系人、产品配件是物理删除。
4. **列表过滤口径不一致。** 产品列表默认只返回 `active`，停用产品会从产品页和所有下拉里消失（`products/repositories.py:515-529`）；客户、供应商、合作伙伴、单证资料不传 `status` 时返回全部，**停用记录仍会出现在下拉里**。
5. **下拉是一次性加载，默认 50 条，无远端搜索。** 出口合同、采购合同的客户/供应商/产品下拉都是一次 `list...()` 调用（`sales/hooks/useExportContractOptions.ts:25-52`、`purchase/hooks/usePurchaseContractOptions.ts:23-45`），后端默认 `limit=50`。超过 50 条的主数据在后两个页面选不到。
6. **唯一会实时回读主数据的地方是打印/导出。** 出口合同打印会实时读客户主联系人（`system/printing/services.py:206-220`）；采购合同模板会实时读供应商地址与主联系人电话/邮箱（`printing/services.py:243-260`），并按 `product_id` 实时读产品图片和包装说明（`printing/services.py:262-287`）。其余页面全部看快照。

### 1.3 产品（`products` / `product_accessories`）

#### 关键字段

| 字段 | 业务作用 |
|---|---|
| `code` | 唯一编码。除展示外，还被「从出口合同生成采购合同」用作回查商品的锚点 |
| `cn_name` / `en_name` | 中英文品名，写入所有下游行快照 |
| `specification` / `model` | 规格、型号，写入下游行快照 |
| `customs_code` | 海关编码，仅主数据登记与列表搜索使用 |
| `tax_rate` / `rebate_rate` | 增值税率、出口退税率。**当前不参与任何计算** |
| `package_info` | 包装说明。采购合同模板打印时会拼进行备注 |
| `unit` | 单位，写入下游行快照 |
| `image_url` | 产品图片。采购合同模板打印时实时读取 |
| `status` | `active` / `inactive` |
| 配件：`accessory_name`、`unit_consumption`、`unit`、`default_supplier_name`、`purchase_split_rule` | 采购合同生成时按「成品数量 × 单耗」展开成采购行；`default_supplier_name` 只是文本，不指向供应商表 |

#### 引用方式

- **下游全部是快照。** 报价行、出口合同行、出货行、库存、出库行、采购合同行、询价行、样品行、QC 行都存 `product_id`（普通 String）+ `product_code`/`product_name`/`specification`/`model`/`unit`（`sales/contracts/models.py:87-94`、`sales/quotations/models.py:62-68`、`sales/shipments/models.py:77-83`、`warehouse/outbound_orders/models.py:71-74`、`purchase/inquiries/models.py:44-46`）。
- **会实时读产品表的三处：**
  1. 从出口合同生成采购合同时，按 `product_id` 读配件；行上没有 `product_id` 时，退化为按 `product_code` 回查（`purchase/contracts/services.py:562-622`）。
  2. 采购合同模板打印，按 `product_id` 读 `image_url` 和 `package_info`（`printing/services.py:262-287`）。
  3. 产品详情「交易记录」和「相关客户」，按 `product_id` 聚合报价、采购、出货、出口合同行（`products/repositories.py:230-259`、`:261` 起）。

#### 改动的影响

| 改动 | 历史单据 | 未结单据 | 打印/导出 |
|---|---|---|---|
| 改中英文名、规格、型号、单位 | 不变，显示旧快照 | 不变；列表和详情都读快照 | 出口合同打印不变；采购模板只读图片和包装，不读名称 |
| 改 `code` | 不变 | 不变；但若从出口合同生成采购合同时行上没有 `product_id`，按新编码回查会失败，报「商品编码 xxx 未关联商品资料」 | 不变 |
| 改 `package_info` | 不变 | 不变 | **采购合同模板下次打印会用新包装说明** |
| 改 `image_url` | 不变 | 不变 | **采购合同模板下次打印会用新图片** |
| 改 `tax_rate` / `rebate_rate` | 无影响 | 无影响 | 无影响；系统里没有计算读取这两个字段，退税额来自核销单，不来自产品 |
| 改配件（增删改） | 不变 | 不变 | 从出口合同生成采购合同时按**当前**配件重算，已生成的采购合同不重算 |

#### 停用与删除

- 产品停用是 `status="inactive"`，无引用拦截（`products/services.py:161-177`）。
- 停用后：产品页看不到（列表默认过滤 active），出口合同/采购合同/报价的下拉也选不到。
- 停用后：历史单据和未结单据照常显示快照；采购合同模板仍能按 `product_id` 读到停用产品的图片和包装（`get_product` 不判断状态）。
- 配件是物理删除（`products/repositories.py:199-216`），删掉后无法从出口合同再生成含该配件的采购行。

#### 使用面

| 页面 / 服务 | 用途 |
|---|---|
| 产品资料页 | 主数据增删改查、图片、配件、导入导出、交易记录 |
| 出口报价 | 产品下拉；行快照；「历史采购参考价」按 `product_id` 查旧报价行 |
| 出口合同 | 产品下拉；行快照；详情/交易记录按 `product_id` 聚合 |
| 采购合同 | 产品下拉；按配件生成采购行；模板打印读图片和包装 |
| 采购询价 | 询价行快照 |
| 样品申请 / 样品登记 | 产品快照 |
| QC 查验 | 查验行 `product_id`/`product_code`/`product_name` 快照 |
| 入库计划 / 入仓 / 出库计划 / 货物出库 | 产品快照；库存表另存 `code`/`name`/`unit` |
| 出货明细 | 出货行快照 |

#### 已知局限

- **没有价格字段。** 报价单价、合同单价、采购单价全靠手填；「历史采购参考价」只能反查旧报价行里手填的 `purchase_reference_price`，不是产品主数据能力。
- **税率、退税率是死字段。** 登记后没有任何计算、校验或报表引用，不能支撑「按产品算退税」。
- **配件默认供应商是纯文本。** 不指向 `suppliers`，供应商改名不联动，也无法按供应商汇总配件需求。
- **产品编码可修改，且生成采购合同时会用编码回查。** 一旦历史合同行没有 `product_id`，改编码就会断链。
- **停用不做引用拦截。** 停用后历史采购合同打印仍会带出该产品的图片和包装。
- **下拉上限 50 条且无搜索。** 产品超过 50 个时，出口合同和采购合同页面选不到后面的产品。
- **删除配件无引用检查。** 已生成的采购合同不会追溯，但后续再生成会少行或直接报错。

#### 停用与删除

- 停用后：客户资料列表仍能看到；报价页、出口合同页的客户下拉 `listCustomers()` 默认不带 `status`，**停用客户仍可被选中新建单据**。
- 停用后：历史单据、未结单据、打印都照常。
- 联系人物理删除。

#### 使用面

| 页面 / 服务 | 用途 |
|---|---|
| 客户资料页 | 主数据增删改查、联系人、信用档案、交易记录 |
| 出口报价 | 客户下拉；表头快照 |
| 出口合同 | 客户下拉；表头快照；打印实时读联系人 |
| 出货明细 | `customer_id`/`customer_name` |
| 出库计划 / 货物出库 | `customer_id`/`customer_name` |
| 收款管理 | 手填 `customer_id`/`customer_name` 快照 |
| 核销退税 / 杂费 / 口岸数据 | 客户名称文本 |
| 单证资料 | `customer_id` + `customer_name` 快照 |
| 产品资料详情 | 按出口合同行的 `product_id` 聚合，再按合同 `customer_id` 汇总客户 |

#### 已知局限

- **没有客户地址、联系人快照。** 出口合同打印不含地址；客户地址后来改了，也无从追溯当时用的是哪个地址。
- **创建单据不校验客户存在与启用。** 可以写入不存在的 `customer_id`，也可以给停用客户下新合同。
- **信用额度、付款条件不参与控制。** 不能做信用额度占用、超额拦截；合同付款条件与客户信用档案没有关联。
- **首付/预收款与客户主数据无关联。** 合同预收款只存 `payer_name` 文本。
- **停用客户仍出现在下拉里。**
- **客户交易记录只聚合出口合同和出货计划。** 不含收款、核销、杂费，不是完整应收台账。

### 1.6 合作伙伴（`partners`）

#### 关键字段

| 字段 | 业务作用 |
|---|---|
| `code` | 唯一编码 |
| `cn_name` / `en_name` | 伙伴名称，写入费用发票与付费申请快照 |
| `partner_type` | 快递 `express`、货代 `freight_forwarder`、保险 `insurer`、承运 `carrier`；写入费用单据快照，并参与财务总览统计 |
| `country` / `address` / `website` | 仅主数据展示，下游不快照 |
| 联系人 | 仅主数据展示；费用单据不引用 |
| `status` | `active` / `inactive` |

#### 引用方式

- 费用发票 `PartnerFeeInvoice`：`partner_id`（普通 String）+ `partner_name` + `partner_type` 快照（`finance/fee_payments/models.py`）。
- 付费申请 `FeePaymentRequest`：同上。
- 财务总览按 `partner_type` 统计启用伙伴数（`finance/overview/repositories.py:134-152`）。
- 财务报表按 `partner_name` 文本筛选（`finance/reports/repositories.py:434-435`）。
- 伙伴详情「交易记录」按 `partner_id` 聚合费用发票与付费申请（`partners/repositories.py:335-365`）。

#### 改动的影响

| 改动 | 历史单据 | 未结单据 | 说明 |
|---|---|---|---|
| 改名称 | 显示旧快照 | 显示旧快照 | 但新建费用发票时，后端会校验 `partner.cn_name == 提交的 partner_name`，改名后前端若仍带旧名会报「合作伙伴名称不一致」（`fee_payments/services.py:290-291`） |
| 改 `partner_type` | 不变，存旧类型 | 不变 | 新建时同样会校验类型一致（`fee_payments/services.py:292-293`） |
| 改地址 / 网站 / 联系人 | 无影响 | 无影响 | 费用单据不含这些字段，也没有打印模板读取 |
| 改银行信息 | 无此项 | 无此项 | 合作伙伴表没有银行账号字段 |

#### 停用与删除

- 停用是 `status="inactive"`，无引用拦截（`partners/services.py:246-265`）。
- 费用发票创建时会校验 `partner.status == "active"`，停用后**不能新登记**费用发票（`fee_payments/services.py:294-295`）；但只有填了 `partner_id` 才走这段校验。
- 历史费用单据、付费申请、财务统计都不受影响。
- 联系人物理删除。

#### 使用面

| 页面 / 服务 | 用途 |
|---|---|
| 合作伙伴页 | 主数据增删改查、联系人、交易记录 |
| 付费管理（费用发票） | `partner_id`/`partner_name`/`partner_type`，可关联出货单 |
| 付费管理（付费申请） | `partner_id`/`partner_name`/`partner_type` |
| 财务摘要 / 经营总览 | 按类型统计启用伙伴数 |
| 财务报表 | 按伙伴名称文本筛选费用 |

#### 已知局限

- **付费表单里 `partner_id` 是手填文本框，不是下拉。** 不填 `partner_id` 也能建费用发票，此时完全不校验伙伴主数据（`finance/forms/feeForms.tsx:23-25`、`FeesView.tsx:283-290`）。
- **出货单没有货代/承运/保险字段。** `ShipmentPlan` 只有 `shipping_method`、`vessel_name`、`container_no`、`booking_no` 等文本，不能结构关联合作伙伴，因此无法按货代统计某票出货的应收应付。
- **没有银行账号、SWIFT。** 付费只能手填 `payment_account`。
- **联系人完全没被使用。** 费用单据不取伙伴联系人，也没有对账单打印。
- **伙伴停用只拦「填了 partner_id」的新费用发票。** 不填 ID 的纯文本费用单照样能建。

### 1.7 单证资料（`document_parties`）

#### 关键字段

| 字段 | 业务作用 |
|---|---|
| `code` | 唯一编码 |
| `party_type` | 收货人 `consignee`、通知人 `notify_party`、开证行 `issuing_bank`、账单通知人 `bill_notify_party` |
| `display_name` | 单据上显示的主体名称 |
| `customer_id` / `customer_name` | 归属客户；ID 是普通 String，名称是快照 |
| `country` / `address` / `contact_person` / `email` / `phone` | 单证收件信息 |
| `bank_name` / `swift_code` / `account_no` / `tax_id` | 开证行等银行信息 |
| `is_default` | 同一 `party_type` + `customer_id` + `owner_user_id` 下只能有一个默认（`document_parties/repositories.py:67-72`、`:160`） |
| `status` | `active` / `inactive` |

#### 引用方式

**目前没有任何下游业务引用它。** 全后端搜索 `document_party`/`DocumentParty`，只命中本模块、菜单种子和权限种子（`masterdata/document_parties/*`、`system/auth/seed_navigation.py`、`seed_permissions.py`）。出口合同、出货明细、报关、财务都没有指向单证资料的字段，也没有任何页面读取它自动带出收货人/通知人/开证行。

#### 改动的影响

- 改名称、地址、联系人、银行账号：**不影响任何业务单据**，因为没有引用。
- 反过来也成立：在这里维护得再完整，出口合同和出货单也不会自动带出。
- `customer_id` 不是外键，客户改名不会改这里的 `customer_name` 快照，也不会反向影响客户。

#### 停用与删除

- 停用是 `status="inactive"`，无引用拦截；停用时强制 `is_default=False`（`document_parties/repositories.py:176-184`）。
- 列表不传 `status` 时仍会显示停用记录；`lookup` 接口用 `active_only=True`，只返回启用记录。
- 没有物理删除入口，只有停用。

#### 使用面

| 页面 / 接口 | 用途 |
|---|---|
| 单证资料页 | 列表、筛选（类型/客户/状态）、详情、新增/编辑/停用 |
| `GET /document-parties/lookup` | 后端已实现按类型 + 客户查启用记录，**前端没有调用点** |
| 其余业务页面 | 无 |

#### 已知局限

- **是一个孤立的主数据库。** 出口合同、出货、单证打印都没有接它，维护后不产生任何业务效果。
- **`lookupDocumentParties` 没有前端调用点。** 前端 API 已封装（`frontend/src/api/masterdata-partners.ts:258-265`），但只有单证资料页自己用 `listDocumentParties`。
- **`customer_id` 是普通 String。** 不能保证归属客户存在，也不能级联。
- **默认标记只在「类型 + 客户 + 创建人」范围唯一。** 换一个业务员看不到别人建的默认单证资料，同一客户可能有多套默认。
- **停用不拦截。** 因为没人引用，所以也谈不上拦截；但也意味着停用不会带来任何业务变化。

### 1.8 本章结论

基础资料这一层目前是「**主数据可维护，业务单据靠快照**」的形态：

- 好处是历史单据不会被主数据改名改价直接影响，账面临时改动风险低。
- 代价是：主数据改了不会回写历史，也不会强制新单据使用最新值；数据一致性完全依赖前端下拉和人工操作。
- 最明显的三个缺口：**没有任何引用拦截、客户/供应商信用额度完全不参与业务控制、单证资料是孤立数据**。
- 进入下一章（报价）时，需要特别记住：报价行的产品信息是快照，客户名称是快照，采购参考价是手填文本；报价不会因为产品主数据或客户主数据后续变化而自动更新。

## 第二章 报价 → 样品 → 出口合同

### 2.1 这条主线在系统里的真实走法

```
客户询价
  ├─ 出口报价：草稿 → 待审批 → 已审批 ──「生成出口合同」──► 出口合同（草稿）
  └─ 打样管理：草稿 → 已发送 → 进行中 → 已完成 ──「载入样品登记」──► 样品登记
                                                              └─► 寄样单：草稿 → 待审核 → 已审核 → 已寄出
出口合同：草稿 → 待审批 → 已审批 ──► 出货明细 / 采购合同 / 收款核销
```

| 衔接 | 系统里是否“一键” | 依据 |
|---|---|---|
| 报价 → 出口合同 | **是**。已审批报价点「生成出口合同」，生成草稿合同并写 `source_quotation_id/no`，报价状态变「已生成合同」 | `sales/quotations/services.py:370-460` |
| 打样申请 → 样品登记 | **是**。打样「已完成」后可点「载入样品登记」；同一申请只能转一次 | `sample/requests/services.py:294-314` |
| 样品登记 → 寄样单 | **半自动**。寄样行必须填样品标识，但不会从样品登记带出；审核时按样品留样量扣减 | `sample/deliveries/services.py:605-642` |
| 报价 ↔ 寄样 | **弱关联**。寄样单的报价号是手填文本；报价详情的「寄样关联」按「客户 + 首个产品」反查已审核/已寄出的寄样单，不按 `quote_id` | `sales/quotations/services.py:500-522` |
| 报价 ↔ 打样 | **无关联**。打样申请没有报价字段，需要人工另建 | `sample/requests/models.py:15-60` |

一句话：**报价到合同是硬衔接，样品内部是硬衔接，报价到样品基本靠人。**

### 2.2 出口报价（`/sales/quotations`）

#### 页面与数据

| 项 | 内容 |
|---|---|
| 菜单 / 路由 | 「出口报价」/ `/sales/quotations`（`frontend/src/app/pages/sales/ExportQuotationsPage.tsx:18-79`） |
| 主表 / 行表 | `export_quotations` / `export_quotation_lines`（`backend/app/modules/sales/quotations/models.py:15-87`） |
| 权限 | 查看 `sales:quotation:view`、编辑 `sales:quotation:edit`、审批 `sales:quotation:approve`、导出 `sales:quotation:export` |
| 指标卡 | 报价单总数、待审批数、已审批数、报价总额（`ExportQuotationListPanel.tsx`） |
| 列表列 | 报价单号、状态、客户、贸易条款、金额、已生成合同号、详情入口 |
| 筛选 | 关键字（单号/客户/贸易条款/产品）、状态、客户（服务端搜索） |

状态筛选**没有「已退回」选项**（`ExportQuotationListPanel.tsx:47-48`），被驳回的报价只能在列表里按客户/关键字找，不能按状态筛。

#### 状态机

| 当前 | 动作 | 结果 | 条件与限制 |
|---|---|---|---|
| 草稿 | 提交审批 | 待审批 | 必须指定审批人，且审批人不能是提交人；审批人要有 `sales:quotation:approve` |
| 待审批 | 审批通过 | 已审批 | 只有被指定的审批人（或有全局审批权的管理员）能操作（`sales/quotations/services.py:250-284`） |
| 待审批 | 驳回 | 已退回 | 必须填驳回原因（`sales/quotations/services.py:286-326`） |
| 待审批 | 撤回 | 草稿 | 仅提交人本人或超管；已生成合同的不能撤回（`sales/quotations/services.py:328-368`） |
| 已审批 | 生成出口合同 | 已生成合同 | 确认日期必填；生成草稿合同；重复点击会被后端拒绝（`sales/quotations/services.py:370-409`） |
| 已退回 | 重新编辑 | 草稿（保存时） | 只有草稿/已退回能载入编辑（`sales/quotations/services.py:124-168`） |

#### 新建与编辑表单

| 字段 | 说明 |
|---|---|
| 报价单号 | 保存后自动生成，页面只读 |
| 报价日期 / 有效期至 | 有效期会优先成为生成合同的「计划出运日」 |
| 客户 | 服务端搜索、只返回启用客户；选中后带出客户名称、币种、贸易条款 |
| 客户名称 | 只读快照 |
| 销售员 | **手填文本**，不是员工下拉；新建时不提交 `sales_user_id`，编辑旧单沿用原 ID |
| 币种 / 贸易条款 / 说明 | 文本 |
| 明细 | **页面只支持一行**：商品标识、产品编号、产品名称、规格、型号、数量、单位、单价、运费方式、运费、采购参考供应商、采购参考价、行备注 |

录入规则与校验：

- 行金额 = 数量 × 单价；**报价总额 = 各行（金额 + 运费）**（`sales/quotations/services.py:552-579`）。
- 数量必须 > 0，单价必须 > 0，运费金额不能为负。
- 客户名称必填；一旦选择客户（传 `customer_id`），服务端校验其存在且启用（不存在 422，停用 409）；不选客户、只填名称时不做主数据校验。
- 销售员名称不校验；新建时没有 `sales_user_id`，编辑旧单会原样回传原 ID（若该员工后来停用，只要 ID 未变仍可保存）。
- 行里的「商品标识」是手填 `product_id`：留空不校验；一旦填写，必须是真实且启用的产品 ID，否则 422。产品编号/名称不校验。
- 只有草稿、已退回可以载入编辑；待审批、已审批、已生成合同都只读。

#### 详情页区块

- 表头：状态、客户、销售员、贸易条款、审批人、有效期、已生成合同号、说明、驳回原因。
- 合同行：产品编号/名称、规格/型号、数量、单位、单价、金额、运费、行备注。
- 历史报价：同一客户 + 同一产品的历史报价对比（`sales/quotations/services.py:462-478`）。
- 采购参考：按行产品汇总的历史采购价参考（`sales/quotations/services.py:479-499`）。
- 寄样关联：同客户 + 首个产品的已审核/已寄出寄样单（`sales/quotations/services.py:500-522`）。
- 操作：载入编辑、提交审批、审批、驳回、撤回、导出 PDF、生成出口合同。

#### 报价转合同时复制什么

`sales/quotations/services.py:411-460` 的复制口径：

| 合同字段 | 来源 |
|---|---|
| 合同日期 | 生成时填的确认日期 |
| 客户 / 客户名称 | 报价的客户与快照 |
| 销售员 | 报价的 `sales_user_id/name` |
| 币种 / 贸易条款 | 报价 |
| 计划出运日 | 报价有效期；没有有效期时用确认日期 |
| 付款条件 | **空字符串**，需要后续在合同里补 |
| 备注 | 报价说明 |
| 明细 | 产品、规格、型号、数量、单位、单价、金额、备注 |

**不复制**：运费方式/运费、采购参考价。因此报价总额（含运费）与合同总额（只含货款）通常不相等。

#### 已知局限

- **页面只能维护一行明细。** 后端 `lines` 是数组，但新增/编辑表单固定只提交一行（`exportQuotationHelpers.tsx:186-205`）。
- **商品标识、销售员是手填文本。** 商品标识填错会被新校验以 422 拒绝；销售员名称与员工账号没有关联。
- **已生成合同后仍能点「生成出口合同」。** 按钮在「已审批/已生成合同」都显示，第二次点击后端报「只有已审批报价可以生成出口合同」；没有幂等键（进入第二批）。
- **状态筛选缺「已退回」**（`ExportQuotationListPanel.tsx:47-48`）。
- **没有打印模板。** 报价只能导出 PDF/CSV，不读取客户地址、联系人和单证资料。

#### 下游单据

| 下游 | 入口 | 条件 |
|---|---|---|
| 出货明细 | 出货明细页从合同行生成 | 合同需已审批；每个合同只取**首个未出货行**，数量不能超过未出货量；同一合同不能重复选，跨合同币种必须一致；**出货明细审批通过后才回写**合同行已出货数量（`sales/shipments/services.py:69-124`、`234`） |
| 采购合同 | 采购合同页「从出口合同生成」 | 合同需已审批；取选中合同的**全部行**，按产品配件汇总数量；产品没有配件明细会直接拒绝；供应商必须存在且启用；采购合同审批通过后才回写合同行已采购数量，重复生成不会被拦截（`purchase/contracts/services.py:168-226`、`614-631`） |
| 收款 | 收款管理手工登记后分配到合同 | 作废前必须没有收款分配（`cancellation.py:56-57`） |
| QC / 跟单 / 仓库 | 以合同或合同行为来源 | 见后续章节 |

#### 快照口径

- 快照：合同号、客户名称、销售员名称、币种、贸易条款、付款条件、合同行产品编号/名称/条码/规格/型号/单价。
- 实时：打印时的客户主联系人；列表里的「已采购/已出货」进度（由下游审批回写合同行字段）；预收款合计。

### 2.7 一条完整走单顺序（照着做）

1. **建报价**：出口报价 → 选启用客户 → 填一行产品、数量、单价、运费 → 保存。
2. **审批报价**：详情 → 提交审批（指定审批人）→ 审批人审批通过。
3. **转合同**：详情 → 生成出口合同 → 填确认日期 → 得到草稿合同。
4. **补合同**：订单中心 → 载入编辑 → 补付款条件、计划出运日、条码/规格/型号 → 保存。
5. **审批合同**：提交审批 → 审批通过。
6. **并行分支**：
   - 采购：采购合同页从出口合同生成 → 审批 → 回写合同行已采购数量。
   - 样品：打样管理新建打样单 → 更新进度到「已完成/客户确认」→ 载入样品登记 → 寄样管理新建寄样单 → 提交审核 → 审核通过 → 更新物流寄出。
7. **出货与收款**：出货明细页从合同行生成 → 出运；收款管理登记收款并分配到合同。
8. **回签与归档**：合同详情登记客户回签；需要时打印单据/导出 PDF。

### 2.8 本章结论

- **报价是价格谈判层，合同是履约层。** 报价审批通过后才允许转合同；转合同只复制主干字段，运费、采购参考价不会带入，条码/规格/型号需要在合同里补齐。
- **样品是独立闭环。** 打样 → 样品登记 → 寄样这条链在样品模块内部是通的，但与报价只有「客户 + 产品」的弱反查。
- **合同是订单中心，也是所有下游的锚点。** 采购、出货、收款、QC、仓库都从合同或其行出发；合同一旦有下游单据就不能作废，只能重开。
- 本批已解决「新建引用不存在/停用主数据」和「下拉截断」两个基础问题；仍未解决的是：**报价 ↔ 样品没有结构化关联、待审批合同无驳回/撤回、签署与预收款无状态/金额约束、生成型动作无幂等键**（后两项进入第二批）。

## 第三章 采购：询价 → 采购合同 → 跟单 → 开票通知

第二章讲的是「客户要什么」（报价 → 出口合同）。这一章讲「我们向谁买、买了多少、到哪一步、发票怎么开」。四个页面看着像一条链，实际上**只有中间一段是自动的**：出口合同审批通过后才能一键生成采购合同，采购合同审批通过后才会自动建跟单计划并回写出口合同行的「已采购数量」；询价与开票通知都不在这条自动链上，它们是各自独立的手工闭环。

### 3.1 这条主线在系统里的真实走法

```
[采购询价]  draft ──发送模板──> sent ──登记报价──> quoted
    │  （不转采购合同，无任何下游）
    └── 手工新建（与下游无关联）

[出口合同] approved ──一键生成──> [采购合同] draft
                                    │ 提交审批（指定审批人）
                                    ▼
                                 submitted ──审批──> approved
                                    │                  │
                                    │                  ├─ 回写出口合同行 purchased_quantity（累加）
                                    │                  ├─ 自动创建跟单计划（6 固定节点）
                                    │                  └─ 自动生成「入库计划」（见第四章）
                                    └─ 作废 cancelled ──重开（仅一次）──> draft
```

**已知缺口/反直觉处**

1. 手工新建只能一行，多产品合同必须走「从出口合同生成」或反复建单。
2. 生成时供应商是自由文本，与询价里「报价行供应商走主数据校验」不一致。

4. 提交后无撤回，只能驳回；驳回后编辑保存会被强制重置为 `draft`，需要重新提交。
5. 提醒（`services.py:506-524`）是「先删后建」，**收票/付款后也不会关闭**，页面上会一直挂着。
6. 全局提醒接口 `/reminders` 没有按数据范围过滤，能看到别人的合同提醒。

### 3.7 一条完整走单顺序（照着做）

1. **询价**：采购 → 采购询价 → 新建（客户 + 单产品 + 数量）→ 发送模板 → 登记 2–3 家供应商报价。注意先发送再报价，否则状态会回退。
2. **出口合同**：按第二章走到「已审批」。（这是采购合同生成的前置条件。）
3. **生成采购合同**：订单流程 → 采购合同 → 从出口合同生成 → 选 1–2 张已审批出口合同 + 供应商 + 交期 + 配件单价 → 保存得到 `draft`。
4. **补合同**：编辑补付款条件、交货日、行价格（只有 `draft`/`rejected` 可改）。
5. **提交审批**：指定审批人（不能是自己）→ 提交。
6. **审批**：审批人通过 → 自动回写出口合同行「已采购数量」、自动建跟单计划（6 节点，首节点已完成）、自动建入库计划。
7. **跟单**：QC/跟单 → 打开该合同的计划 → 逐节点完成（或由样品/QC 事件触发）。主管若看不到下属计划，需要 `view_all`。
8. **开票通知**：采购单据 → 开票通知 → 生成（手填报关单号 + 供应商）→ 发送 → 收到发票后登记收票。
9. **反向修正**：若合同要废，先在详情作废（需无入库/QC/开票/付款/样品/跟单后续节点）→ 状态 `cancelled` → 需要时重开（仅一次）。作废会自动扣减出口合同行已采购数量。

### 3.8 本章结论

- **这条链只有三处是「一键」的**：出口合同 → 采购合同（生成）、采购合同审批 → 回写已采购数量 + 建跟单计划、采购合同审批 → 建入库计划。开票通知看似「从合同生成」，实际是手填合同号与商品行后按供应商分组，其余全是手工填写。
- **询价是独立的价格记录，不是采购合同的来源。** `quoted` 之后没有下游；采购合同只能从出口合同生成或手工新建。把询价当「采购前置」是产品叙事，不是代码事实。
- **快照与回写要分清**：合同头/行是生成时的快照，之后不随出口合同变；只有 `purchased_quantity` 与 `received_quantity` 是实时回写。所以「出口合同改了数量，采购合同不会自动跟」。
- **审批是这条链的真正开关**：回写、建跟单、建入库都挂在 `approved` 之后；开票通知不依赖审批状态。这也意味着审批前的一切修改都是安全的。
- **最大的结构性缺口是「多对一」**：一张出口合同行被多张采购合同认领时，只有第一张 approved 会回写，其余静默跳过；而作废/重开又只做一次。「已采购数量」在不同路径下可能对不上，需要人工核对。
- **三个模块的 `view_all` 权限码都声明了但没读**，实际数据范围完全由 `data_scope` 决定；跟单更严格，默认只给本人。权限配置页上勾了 `view_all` 不会有任何效果，这是最容易被当成 bug 的地方。
- **开票通知是整章最「薄」的一环**：不读报关单、不校验合同外键、收票不回写金额、`code` 会撞唯一键。它可以当「催供应商开票的登记表」用，但不能当财务凭证。

## 第四章 仓库：入库、出库、库存

仓库菜单只有四个页面：入库计划、入仓、出库计划、货物出库（`backend/app/modules/system/auth/seed_navigation.py:233-271`；`frontend/src/app/routes.ts:91-111`），四个菜单都有实体页面，没有空壳菜单。**库存不是独立页面**：`backend/app/modules/warehouse/inventory/` 只有 `models/providers/repositories/services`，模块自身没有独立 API 路由和前端路由；库存余额/流水只能从入库单、出库单详情里的内嵌区块看到，属于「有代码、无入口」。库存的唯一来源，是入库单或出库单**审批通过**这一动作。

### 4.1 这条主线在系统里的真实走法

```
采购合同审批通过
  └─ 自动建入库计划（1 合同 1 计划，计划行=合同行未入库数量）
       └─ 排库位（计划 → scheduled）
            └─ 从计划生成入库单（只能是草稿，必须选计划）
                 ├─ formal：最新 QC 必须 completed/passed → 审批 → 库存 available +
                 │           └─ 回写入库计划行 + 采购合同行 received_quantity
                 └─ pending_inspection：审批 → 库存 pending_inspection +
                             （不回写、不转 available、计划不关闭）

出货明细审批通过
  └─ 人工生成出库计划（必须选已审批出货明细，来源类型只有 shipment_plan）
       └─ 排库位（计划 → scheduled）
            └─ 从计划生成出库单（只能是草稿，必须选计划）
                 └─ 审批 → 库存 available −
                      └─ 回写出库计划行 outbound_quantity（不回写出货明细/出口合同）
```

| 衔接 | 是否「一键」 | 依据 |
|---|---|---|

| 入库单 → 库存 | **是**。审批通过时逐行写余额与流水 | `backend/app/modules/warehouse/inbound_orders/services.py:487-519` |
| 入库单 → 采购合同行 | **仅 formal**。审批时回写 `received_quantity` 并刷新合同统计；`pending_inspection` 不回写 | `backend/app/modules/warehouse/inbound_orders/services.py:215-222`、`:521-529`；`backend/app/modules/purchase/contracts/repositories.py:253-263` |

#### 4.6.3 余额和流水，哪个是真账

| 问题 | 结论 | 依据 |
|---|---|---|
| 余额是否由流水汇总 | **否**。余额是独立表，入库/出库时直接 `+= / -=`，不读流水；流水只追加，没有更新/删除接口 | `backend/app/modules/warehouse/inventory/repositories.py:106-107`、`:156`、`:160-200` |
| 库存校验以谁为准 | **余额表**；出库只检查 `available_quantity`，不看流水 | `repositories.py:111-158` |
| 两者不一致以谁为准 | **余额表是业务真账，流水只是明细证据**；系统没有对账入口，也没有「按流水重算余额」的功能 | `inventory/services.py` 只有 `list_balances` / `list_ledgers`；`backend/app/api/v1/inbound_orders.py:60-94` 只有两个只读接口 |
| 待检/锁定量会不会用 | **都不会**。`pending_inspection_quantity` 只增不减，没有 QC 转 available 的动作；`locked_quantity` 默认 0，从未被写入 | `inbound_orders/services.py:487-500`；`inventory/models.py:27`；`inventory/repositories.py:98-99`、`:146-147` |
| 有没有对账入口 | **没有**。只有入库单/出库单详情里的「余额 / 流水」内嵌查询，且余额是全局关键字搜索，不按当前单据过滤 | `frontend/src/app/pages/warehouse/views/InboundOrderDetailPanel.tsx:129-216`；`backend/app/modules/warehouse/inbound_orders/services.py:333-381` |

#### 4.6.4 幂等与并发

- 入库/出库审批的「幂等」只有一层：服务层先判断 `status == submitted`，然后仓储层无条件改成 `approved`（`inbound_orders/services.py:191-192`；`repositories.py:283-298`；`outbound_orders/repositories.py:306-330`）。
- 流水表没有 `(source_type, source_id, line_id)` 唯一约束（`inventory/models.py:41-65`），余额表也没有 `(warehouse, location, product, unit)` 唯一约束（`inventory/models.py:15-38`）；行级 `received_quantity/outbound_quantity` 也是「读-加-写」，没有版本号（`inbound_plans/repositories.py:298`；`outbound_plans/repositories.py:319`）。并发下同一张单被审批两次，存在**重复加/减库存**的窗口。

#### 4.6.5 库存的页面入口到底在哪

- **没有独立菜单、没有独立路由**：`frontend/src/app/routes.ts:91-111` 只有四个仓库路由；种子菜单也只有四条（`backend/app/modules/system/auth/seed_navigation.py:233-271`）。
- 库存阅读入口只有两个：入库单详情、出库单详情里的「库存余额 / 库存流水」区块（`InboundOrderDetailPanel.tsx:129-216`；`OutboundOrderDetailPanel.tsx:138-244`）。余额只按一个 `q` 关键字查（默认取当前单据首个产品编码），不传 `warehouse_id/location_id/product_id`；流水才按 `source_id = 当前单据` 查（`frontend/src/app/pages/warehouse/hooks/useInboundInventory.ts:34-39`；`useOutboundInventory.ts:34-39`）。
- 库存接口挂在入库单路由下，权限也用 `warehouse:inbound_order:view`（`backend/app/api/v1/inbound_orders.py:60-94`；`inbound_orders/services.py:342`、`:372`）。出库详情里的库存区块同样复用这套接口。

### 4.7 一条完整走单顺序

1. **采购合同审批**：订单流程 → 采购合同 → 提交 → 审批通过。系统自动建一张入库计划，行数量取合同行 `unreceived_quantity`（`backend/app/modules/purchase/contracts/services.py:353-356`、`:636-647`）。
2. **排入库库位**：入库计划 → 选中计划 → 填计划日期、仓库、库位、经办人 → 保存，状态变 `scheduled`（`InboundPlansPage.tsx:657-741`；`inbound_plans/repositories.py:266-288`）。
3. **QC（formal 必需）与生成入库单**：先把该采购合同的 QC 做到 `completed/passed`，否则 formal 审批会被拒（`inbound_orders/services.py:203-205`、`:472-475`）；再到入仓 → 「生成 / 审批」→ 选计划 → 选 formal 或 pending_inspection → 填仓库/库位/经办人 → 生成草稿（`InboundOrderWorkflowModal.tsx:43-201`）。
4. **提交与审批入库**：选审批人 → 提交；审批人审批通过。formal 会加可用库存、回写计划行和采购合同行；pending 只加待检库存（`inbound_orders/services.py:183-242`）。
5. **出货明细审批**：出口合同 → 出货明细 → 提交 → 审批通过。此时合同行 `shipped_quantity` 已回写，但**不会**自动生成出库计划（`backend/app/modules/sales/shipments/services.py:229-255`）。
6. **生成出库计划**：出库计划 → 「生成 / 排库位」→ 选已审批出货明细 → 生成 `planned` → 填仓库/库位/经办人 → `scheduled`（`OutboundPlansPage.tsx:698-843`）。
7. **生成出库单**：货物出库 → 「生成 / 审批」→ 选出库计划 → 选 formal 或 exception → 填日期/仓库/库位/经办人 → 生成草稿（`OutboundOrderWorkflowModal.tsx:40-175`）。
8. **提交与审批出库**：提交审批人 → 审批通过。formal 要求整行数量等于计划剩余量；审批时扣可用库存、写出库流水、回写计划行 `outbound_quantity`，全部完成则计划 `closed`（`outbound_orders/services.py:179-237`）。
9. **异常处理**：已审批入库/出库单不能作废或冲销；库存错了只能反向再开一张单人工调平。待检入库想转可用，目前没有入口，只能等后续改造。

### 4.8 本章结论

- **仓库四页是「两段计划 + 两段执行」**，真正的库存动作只有两个：入库单审批加库存、出库单审批减库存；计划本身不碰库存（`inbound_orders/services.py:487-519`；`outbound_orders/services.py:437-475`）。
- **库存没有页面，也没有库存主数据**。余额/流水只能从入库单或出库单详情看，余额查询还是全局关键字搜索；仓库、库位都是订单上的字符串，前端用 `wh-factory/wh-company/wh-ningbo` 这类假 ID 兜底（`routes.ts:91-111`；`inboundOrderHelpers.ts:35-46`；`outboundOrderHelpers.ts:77-89`）。
- **入库计划是自动的，出库计划是手动的**。采购合同审批后自动建入库计划；出货明细审批后必须人工去出库计划页生成，且出货明细一旦生成出库计划就不能撤回/驳回（`purchase/contracts/services.py:353-356`；`outbound_plans/services.py:63-71`；`sales/shipments/services.py:405-412`）。
- **formal 才是「真入库」**：只有 formal 入库会回写采购合同行 `received_quantity`、推进计划行状态、触发跟单节点；`pending_inspection` 只增加待检库存，不回写、不转换、不关计划（`inbound_orders/services.py:215-222`、`:487-529`）。
- **余额是独立真账，流水只是证据**。余额表直接加减，不由流水汇总；没有盘点、调拨、手工调整、按流水重算或对账入口；两表不一致时只能人工发现（`inventory/repositories.py:106-107`、`:156`；`inventory/services.py:80-171`）。
- **出库校验的是「仓库 + 库位 + 产品 + 单位」的可用量**，没有批次/效期/库存状态维度；不预占库存，`locked_quantity` 从未使用。部分出库在页面上做不了，只能 API + `exception` 模式（`inventory/repositories.py:369-391`；`outbound_orders/services.py:424-435`）。
- **最大的结构性风险是幂等**：审批是「先读状态、再无条件改状态」，流水/余额都没有来源唯一键；并发或重复审批可能重复过账（`inbound_orders/repositories.py:283-298`；`inventory/models.py:15-65`）。
- **状态显示有三处错位**：入库计划行后端写 `closed`、出库计划行写 `shipped`，前端都只认 `completed`；计划枚举里的 `cancelled` 前后端都没有入口，属于「代码有、业务不可达」（`InboundPlansPage.tsx:137-142`；`OutboundPlansPage.tsx:162-167`；`inbound_plans/schemas.py:16`；`outbound_plans/schemas.py:19`）。

## 第五章 财务：收款、付款、核销、退税、报表

财务菜单共 11 个入口（财务摘要 + 10 个子页面），另加一个独立菜单「老板看板」：财务摘要、经营总览、收款管理、付款管理、付费管理、核销退税、杂费管理、结算核算、报销管理、口岸数据、财务报表（`backend/app/modules/system/auth/seed_navigation.py:284-402`；`frontend/src/app/routes.ts:116-195`）。除「老板看板」用 `reporting:view` 外，其余全部只校验 `finance:view`，没有按岗位拆分应收、应付、税务权限。

财务模块**没有统一单据或审批引擎**。它由三部分拼成：

1. 独立录入的财务单据：银行水单、供应商发票、付款申请、合作伙伴费用发票、付费申请、报销单、核销单、退税登记、结算单。
2. 对业务单据的**只读汇总**：应收来自出口合同与水单分摊的实时相减；经营总览来自出运单上已存的金额字段。
3. 两张独立报表查询栈：财务报表按单据表逐张查，老板看板按合同/出运/结算再查一遍。

所以「同一个数字」在财务里通常有多个来源，本章最后一节专门对比。

### 5.1 钱在系统里的真实走法

```
出口合同审批通过（total_amount）
  └─ 银行水单登记（收款）
       └─ 认领（选业务员）
            └─ 分摊（合同 / 发票 / 预收）
                 └─ 应收余额 = 合同 total_amount − 该合同分摊合计
                      （查询时实时算，不落表）

采购合同 → 开票通知（tax_invoice_status=received）
  └─ 供应商发票登记
       └─ 付款申请（submitted）
            └─ 审批 = 付款完成（paid_amount = 审批金额）
                 └─ 发票 paid_amount 重算 → paid / partial

出运单审批通过
  └─ 合作伙伴费用发票登记
       └─ 付费申请（submitted）
            └─ 审批 = 付费完成，逻辑同上

核销单登记（可退税额手填）
  └─ 登记报关回单 → 登记核销号 → 登记退税
       └─ 出运单 profit_amount += 退税额
            └─ 结算快照按结算日再取一次退税

结算核算（创建即锁定，无审批）
  └─ 销售收入 = 出运单 receivable_amount
       采购成本 = 出运单 payable_amount
       退税/合作方费用/杂费 = 按结算日重新汇总
       └─ 毛利 = 收入 + 退税 − 成本 − 费用 − 手工成本
```

| 衔接 | 是否自动 | 依据 |
|---|---|---|
| 出口合同 → 应收 | **实时查询**，没有应收表、没有余额快照 | `backend/app/modules/finance/receipts/repositories.py:301-338`、`:382-391`、`:482-492` |
| 水单 → 应收 | **人工分摊后才冲减**，只认带 `contract_id` 的分摊 | `receipts/repositories.py:382-391`；`receipts/services.py:218-236` |
| 供应商发票 → 付款申请 | **人工**，发票来自开票通知且通知必须已收票 | `finance/payments/services.py:267-289` |
| 付款申请 → 发票已付 | **审批即付款**，同一事务写分摊并重算发票状态 | `payments/services.py:187-234`；`payments/repositories.py:317-337` |
| 出运单 → 费用发票 | **人工**，出运单必须已审批 | `finance/fee_payments/services.py:300-315` |
| 核销单 → 退税 | **人工登记**，可退税额来自核销单录入值 | `finance/tax_refunds/services.py:46-80`、`:156-189` |
| 退税 → 出运单利润 | **自动加算**，直接把金额加到 `profit_amount` | `tax_refunds/repositories.py:260-274` |
| 出运单/费用/退税 → 结算 | **创建结算时一次性快照**，之后不再同步 | `settlements/repositories.py:116-143`；`settlements/services.py:38-82` |
| 结算/出运 → 报表与看板 | **无关联**，各自再查一遍 | `finance/overview/repositories.py:64-90`；`reporting/statistics/services.py:50-118` |

### 5.2 收款与应收

**状态机**

| 当前状态 | 动作 | 结果 | 条件/限制 |
|---|---|---|---|
| `unclaimed` | 认领 | `claimed` | 有 `finance:view` 或 `sales:contract:view` 即可；可选择任意业务员（`receipts/services.py:113-136`、`:318-323`） |

**应收余额怎么算**

`list_receivables` 每次请求现算：只取 `approval_status = "approved"` 的出口合同，左连接「按 `contract_id` 汇总的分摊金额」，余额 = `max(合同 total_amount − 分摊合计, 0)`（`receipts/repositories.py:382-425`、`:482-492`）。合计条使用同一子查询，只把负余额截成 0 再求和（`:340-380`）。

由此可以明确回答本章开头的问题：

- **余额是实时算的，不落表**。没有应收账款表、没有余额快照、没有账龄字段，也没有按到期日分桶。
- **只认合同级分摊**。一条分摊只能挂一个合同；没有 `contract_line_id`，所以不能把一笔钱分到合同行。
- **预收不一定冲应收**。`receipt_type=advance` 是水单类型，`allocation_type=advance` 是分摊类型；只有分摊时填了 `contract_id` 才会进入应收汇总（子查询条件 `contract_id IS NOT NULL`）。
- **能一分钱分给两个合同，但不能一条分摊拆两个合同**。同一水单可分多次、每次一个合同；金额精度 `Numeric(14,2)`，最小 0.01。
- **没有超额校验**。分摊只校验「不超过水单未分摊额」，不校验合同总额；合同已收满后仍可继续分摊，应收余额被截成 0，超收部分在应收页不可见。

### 5.3 付款、付费、报销：三张单，不是一张

| 维度 | 付款申请 | 付费申请 | 报销单 |
|---|---|---|---|
| 表 | `finance_payment_requests` | `finance_fee_payment_requests` | `finance_reimbursements` |
| 来源 | 供应商发票（来自采购开票通知，通知必须已收票） | 合作伙伴费用发票（出运单必须已审批） | 无来源单据，财务/员工直接填 |
| 类型 | `prepayment` / `goods_payment` / `other` | 费用类型 `fee_type` | `travel` / `office` / `entertainment` / `other` |
| 创建后状态 | 直接 `submitted` | 直接 `submitted` | 直接 `submitted` |
| 审批 | 只有通过，没有驳回 | 只有通过，没有驳回 | 可通过或驳回 |
| 付款动作 | **审批即付款**：`approved_amount` 与 `paid_amount` 同时写入 | **审批即付款**，同上 | **分两步**：先审批，再「付款」写 `paid_at` |
| 是否允许自审 | 否（申请人不能审批） | 否 | **没有校验**，申请人可为任意用户，审批人只校验被指派与权限 |
| 单号 | 服务端按编号规则生成 | 服务端生成 | **由请求体传入** `reimbursement_no` |
| 撤销/编辑 | 无 | 无 | 无 |

依据：`finance/payments/services.py:187-234`、`:316-329`；`finance/payments/models.py:15-121`；`finance/fee_payments/services.py:199-246`、`:329-356`；`finance/reimbursements/services.py:46-84`、`:119-179`；`finance/reimbursements/models.py:15-48`；`finance/reimbursements/schemas.py:7-24`。

**应付余额**同样没有落表：供应商发票/费用发票的 `paid_amount` 在每次审批后按分摊汇总重算，状态变为 `unpaid/partial/paid`（`payments/repositories.py:317-337`）；应付列表直接由发票未付金额推导（`payments/services.py:236-265`）。

三者的共同缺口：

- **没有统一付款凭证**。付款申请、付费申请、报销各自记「已付」，没有统一的付款单、银行账户流水、付款批次，也没有和银行水单双向关联。
- **付款账户是自由文本**。`payment_account` 没有主数据校验，填错不影响任何校验。
- **审批没有状态条件更新**。付款/付费审批都是「先读 `submitted`、再无条件写 `approved`」，并发时两个请求都可能通过校验并各自写一条分摊（`payments/services.py:205-225`；`payments/repositories.py:267-293`）。
- **付款申请不可驳回、不可撤回**。`rejected` 在状态枚举里存在，但没有任何接口能到达（`payments/schemas.py:9`；`api/v1/finance/payments.py:23-126`）。

### 5.4 核销单与退税

| 项 | 内容 |
|---|---|
| 菜单 / 路由 / 页面 | 「核销退税」/ `/finance/tax`（`frontend/src/app/routes.ts:151-156`）；页面 `frontend/src/app/pages/finance/views/TaxView.tsx` |
| 后端 | 服务 `backend/app/modules/finance/tax_refunds/services.py`；接口 `backend/app/api/v1/finance/tax_refunds.py:22-120` |
| 数据表 | `finance_verification_documents`（核销单）、`finance_verification_tax_refunds`（退税登记）（`tax_refunds/models.py:15-75`） |

**这里的「核销」不是应收核销**。系统没有「收款与发票/合同的核销单」，也没有坏账核销。`核销单`是一张出口收汇核销单的登记卡：领用日期、有效期、归属业务员、关联出运单、可退税额、报关回单与核销号。它与应收账款、银行水单没有外键或金额关联。

**流程与状态**

| 当前状态 | 动作 | 结果 | 条件 |
|---|---|---|---|
| （无） | 登记核销单 | `issued` | 必填领用日期、币种、可退税额（>`0`）；出运单可选（`tax_refunds/services.py:46-80`） |
| `issued` / `customs_receipt_registered` | 登记报关回单 | `customs_receipt_registered` | 填回单日期（`services.py:106-127`） |
| `customs_receipt_registered` | 登记核销号 | `verified` | 状态必须已登记报关回单（`services.py:129-154`） |
| `verified` / `refunded` | 登记退税 | `refunded`（累计退完） | 币种一致、金额不超过未退税额（`services.py:156-189`、`:239-249`） |

**退税额从哪来**

- **来自核销单上手填的 `refundable_amount`**，不是产品主数据的退税率，也不是报关金额×税率。产品主数据虽然有 `tax_rate` / `rebate_rate`，财务链路没有读取（`tax_refunds/schemas.py:17-29`；`tax_refunds/repositories.py:260-274`）。
- 每笔退税在 `finance_verification_tax_refunds` 单独登记，核销单的 `refunded_amount` 由登记汇总刷新。
- 若核销单关联了出运单，登记退税时会**直接做加法**：`shipment.profit_amount += amount`，并按新的利润重算利润率（`tax_refunds/repositories.py:260-274`）。
- 没有关联出运单时，退税仍计入财务报表的退税统计，但不进入任何出运单利润。

### 5.5 结算核算

| 项 | 内容 |
|---|---|
| 菜单 / 路由 / 页面 | 「结算核算」/ `/finance/settlement`（`frontend/src/app/routes.ts:165-170`）；页面 `frontend/src/app/pages/finance/views/SettlementView.tsx` |
| 后端 | 服务 `backend/app/modules/finance/settlements/services.py`；接口 `backend/app/api/v1/finance/settlements.py:22-100` |
| 数据表 | `finance_financial_settlements`、`finance_profit_cost_links`（`settlements/models.py:15-70`） |

**建单口径**（`settlements/services.py:38-82`；`settlements/repositories.py:116-143`）：

- 销售收入 = 出运单 `receivable_amount`（出运时快照，不是实际收款）。
- 采购成本 = 出运单 `payable_amount`（出运时人工填的预估，不是采购合同实际结算）。
- 合作方费用 = 按 `settlement_date` 汇总费用发票金额（不是实付金额）。
- 杂费 = 按 `settlement_date` 汇总杂费分摊。
- 退税 = 按 `settlement_date` 汇总退税登记。
- 毛利 = 收入 + 退税 − 采购成本 − 合作方费用 − 杂费 − 手工成本（`settlements/repositories.py:222-251`）。

结算单创建即 `locked`，没有审批、没有反结算；同一出运单只靠应用层 `get_settlement_by_shipment` 防重，数据库没有唯一约束（`settlements/services.py:45-48`）。创建后只允许追加手工成本，追加时重算毛利；新的退税、费用发票、杂费不会回写已生成的结算单。

### 5.6 财务报表、经营总览、老板看板：三套查询

| 入口 | 数据来源 | 金额口径 | 是否跨币种相加 |
|---|---|---|---|
| 财务摘要 / 经营总览 | 出运单（`ShipmentPlan`）、开票通知、样品费、合作伙伴 | 出运单上的 `receivable_amount/payable_amount/profit_amount` 存量字段 | **是**：按币种分组后再把各币种原值相加，标签写「多币种」 |
| 财务报表 | 六张报表各自查各自的单据表 | 水单分摊、付款申请、付费申请、核销单、退税登记 | 否，按币种分组展示 |
| 老板看板 | 出口合同、采购合同、出运单、结算单 | 合同金额、出运应收/利润、结算毛利 | **是**：`summary` 把各币种原值直接相加，标签写「多币种」 |

依据：`finance/overview/repositories.py:64-90`、`overview/services.py:41-57`、`:118-126`；`finance/reports/report_definitions.py:8-130`；`reporting/statistics/services.py:88-118`、`:272-276`。

**财务报表六张**（`finance/reports/report_definitions.py:8-130`；接口 `backend/app/api/v1/finance/reports.py`）：

1. 水单使用情况明细表：`finance_bank_receipts` + `finance_receipt_allocations`，按分摊日期。
2. 银行水单汇总表：`finance_bank_receipts`，按收款日期、币种/经办人。
3. 货款支付情况查询：`finance_payment_requests`，未付 = 申请金额 − 已付金额。
4. 费用支付情况查询：`finance_fee_payment_requests`，同上。
5. 报关回单催收查询：`finance_verification_documents`，默认只看未登记回单。
6. 申报退税统计：`finance_verification_documents` + `finance_verification_tax_refunds`，可退来自核销单、已退来自退税登记。

**这三处不是同一套查询**：

- 经营总览的「应收」是出运单上的**计划应收**，不是 5.2 的合同应收余额；它不扣任何收款。
- 经营总览的「利润」是出运单存值，包含退税加算；结算毛利是另一套快照公式，两者可能不等。
- 老板看板的汇总把出口合同额、出运应收、结算毛利放在同一个 `summary` 里相加跨币种，且 `approval_status` 过滤只作用于合同/出运，不作用于结算（`reporting/statistics/services.py:50-104`；`reporting/statistics/repositories.py` 的 `list_settlements` 只按日期过滤）。
- 财务报表的「已付/未付」是付款申请维度，和经营总览的「应付」不是同一张表，也不一定同期。

### 5.8 本章结论

- **钱从合同到收款是断开的**：出口合同只提供总额，银行水单要人工登记、认领、分摊；应收余额在查询时用「合同额 − 带合同的分摊」现算，不落表、不分行、不算账龄（F-01～F-03）。
- **应收余额谁在算**：`ReceiptRepository.list_receivables` 在算，前端只是展示；经营总览里的「应收」不是这个数，而是出运单上的计划应收，两者不能混用。
- **收款的分配只到合同，不到合同行**：一笔水单可拆给多个合同，一笔分摊不能拆给多个合同；能超收，能分给任意客户/任意状态的合同，分错不能撤（F-03、F-04）。
- **付款申请、付费、报销不是同一张单**：付款和付费按「供应商发票 / 合作方费用发票」分表，审批即付款；报销是独立表，先审批再付款，且可自审；三者没有统一付款凭证（F-06～F-08）。
- **核销与退税是单证链，不是应收核销**：核销单登记报关回单和核销号，退税额来自核销单手填的 `refundable_amount`，不来自主数据税率；退税登记直接加出运单利润，和应收、收款没有金额关系（F-09、F-10）。
- **报表不是同一套口径**：财务摘要/经营总览看出运单存值，财务报表看单据表，老板看板看合同+出运+结算；三处各算各的，且前两处跨币种直接相加（F-11～F-15）。

## 第六章 系统设置与工作台

>
> 口径同前：权限码取 `backend/app/modules/system/auth/seed_navigation.py` 与 `seed_permissions.py`；菜单过滤看 `auth/repositories.py`；前端可访问性看 `routes.ts` 的 `canAccessPath`；数据范围看 `auth/data_scope.py` 与 `data_scope_rules.py`。

### 6.1 权限是怎么落到菜单和路由上的

链路上有四层，只有后两层是真正的拦截：

| 层 | 做什么 | 代码 |
|---|---|---|
| 角色 → 权限码 | 一个角色挂多个权限码；用户可挂多个角色，权限取并集；`super_admin` 权限会在登录时展开成全部权限码 | `auth/repositories.py:533-574`；`auth/services.py:88-114` |
| 权限码 → 菜单 | 菜单行带 `required_permission`，登录后按权限码**精确匹配**过滤，返回 37 条菜单路径 | `auth/repositories.py:116-138`；`seed_navigation.py:21-62` |
| 菜单 → 前端路由 | 路由定义本身不带权限字段；`canAccessPath` 比较该路由的 `menuPath` 是否在会话菜单里 | `routes.ts:428-431`；`App.tsx:235-236` |
| 接口 → 服务 | 每个业务服务在方法开头 `_require(current_user, "xxx")`，这是唯一的强校验 | 例：`warehouse/stocktakes/services.py:57-179` |

几个直接结论：

- **菜单只是可见性，不是授权**。把 `/finance/receipts` 直接输入地址，前端会拦；但只要接口层没 `_require`，就仍可被调用。目前业务模块基本都有服务级 `_require`，工作台和通知类接口按“本人数据”设计，没有额外权限码。
- **财务 11 个页面共用 `finance:view` 一个权限码**（全部 `menuPath: '/finance'`）。拿到 `finance:view` 就能进收款、付款、报销、结算、报表全部页面，无法只给“看报表不给看付款”。
- **四个工作台子页没有单独权限**：`/workspace/todos`、`/workspace/schedules`、`/workspace/notifications`、`/workspace/announcements` 的 `menuPath` 都是 `/`，只要有 `dashboard:view` 就能直接访问 URL。
- **权限变更即时生效于接口、滞后于菜单**：`get_current_user` 每次请求重算权限与菜单，但前端会话里的菜单是登录时缓存的，撤权后旧页面仍可点，直到刷新或重新登录；此时接口会拒绝（前提是该接口有校验）。

### 6.2 角色、权限码与数据范围

权限码分四类（功能、数据、字段、流程），四类都有声明，但执行程度不同：

- **功能权限**：`_require` 校验，覆盖绝大多数写操作。
- **字段权限**：只有客户/供应商的信用额度做了字段级控制，`*:credit:view` 决定是否返回额度，`*:credit:edit` 决定能否改（`masterdata/customers/services.py:325-338`、`suppliers/services.py:327-334`）。
- **数据权限有两套机制**：主机制是角色上的 `data_scope` 字段（`self` / `department` / `department_tree` / `all`），多角色取最宽（`data_scope_rules.py:4-22`），由 `DataScopeResolver` 解析成用户 ID 集合（`data_scope.py:5-36`）；辅机制是 `*:view_all` 权限码，命中则直接跳过数据范围。
- **但 `view_all` 只在两个模块真正生效**：QC（`quality/inspections/services.py:671-672`）和跟单（`followup/services.py:490-496`）。权限表里共有 22 个 `:view_all` 码，其余 20 个（销售合同/报价/出货、采购合同/询价/开票通知、出入库单/计划/盘点、基础资料、样品）声明了、在权限弹窗里可勾选，但没有任何服务读取；这些模块“能否看全部”只由角色 `data_scope` 决定。勾了不生效，容易误配。

数据范围的实际覆盖面并不均匀：

| 有数据范围 | 没有数据范围 |
|---|---|
| 客户/供应商/合作伙伴/单证主体、采购合同/询价/开票通知、销售合同/报价/出货、仓库四类单据+盘点、QC、样品、跟单、单据打印 | **全部财务模块**（收款、付款、付费、报销、核销退税、杂费、结算、报表、经营总览、老板看板） |

- 财务只要 `finance:view` 就看全公司的钱，不区分部门/业务员；销售合同却按 `data_scope` 过滤。这是当前最大的越权盲区。
- 演示种子建了 5 个业务角色（业务主管、采购、财务、仓库、QC），`data_scope` 全是 `all`（`seed_users.py:7-15`）；生产系统角色只有超管（`seed_navigation.py:4-7`）。也就是说**开箱即用时部门结构对数据没有任何影响**，只有新建 `self`/`department` 角色后才会生效。

**审批人范围与数据范围是两回事**：

- 选审批人只校验“目标用户是否拥有指定权限码”，不看部门、不看上下级（`auth/assignees.py:4-26`）。
- 审批时只校验“我是不是被指派的审批人，或我是不是超管”（`auth/permissions.py:10-21`）。
- 财务付款/付费把审批门槛设成 `finance:view`（`finance/payments/services.py:129-135`），等于“能看财务就能审批”，没有独立的审批权限码。
- `/api/v1/auth/users` 对任何登录用户返回全部在职员工（含超管），用于选审批人/待办指派，没有权限码或部门限制。

### 6.3 组织、部门与公司信息

组织管理是一个长页面，四块内容共用一套超管校验（`organization/OrganizationUsersPage.tsx:38-57`）：

| 区块 | 能做什么 | 关键约束 |
|---|---|---|
| 公司信息 | 维护公司抬头、地址、联系方式等单例 | 只被单据打印读取（`system/printing/services.py:174`），合同/发票/报表不读 |
| 部门 | 增删改、树形父子 | 删除只校验“部门内没有用户”（`organization_services.py:328-346`），**不校验子部门**；可删父部门留下悬挂 `parent_id` |
| 角色 | 增删改、勾权限、设数据范围 | 删除校验“没有用户在用”（`:439-457`）；不能把自己所在角色的 `super_admin` 权限去掉（`:348-377`） |
| 用户 | 新建（返回初始密码）、改资料/部门/角色、停用、重置密码 | 不能停用自己（`:219-244`）；无密码强度策略；无登录失败锁定 |

部门结构目前只有两个用途：

1. `data_scope = department / department_tree` 时，解析出本部门或子树用户，用于列表过滤和单据可见性。
2. 组织管理页自身的展示与筛选。

它**不参与**审批路由、不参与待办分配、不参与报表分组。报销单上的“部门”是前端自由文本，不落部门表（`finance/reimbursements/models.py:27`、`schemas.py:50`），组织调整不会回溯历史报销。

所有组织操作（建用户、改角色、改权限、重置密码、停用、改公司信息）都没有 `record_audit`。

### 6.4 MCP 接入

MCP 是把系统能力暴露给外部 AI 客户端的入口，范围很窄：

- **只暴露 3 类资源、15 个工具**：产品（列表/详情/创建/更新/删除）、客户（同 5 个）、出口合同（同 5 个）（`mcp/server.py:259-449`；`system/mcp_settings/services.py:15-49`）。仓库、财务、采购、QC 全部没有暴露。
- **鉴权链**：外部请求带 `Authorization: Bearer <token>` → 校验签名与过期 → 查 `mcp_settings` 的全局开关 → 校验令牌版本未轮换 → 还原成某个系统用户（`mcp/credentials.py:88-117`）。
- **令牌身份 = 签发人本人**：只有 `system:super_admin` 能签发，签发时绑定当前超管用户 ID（`mcp_settings/services.py:91-109`），有效期 30 天；重新签发会使旧令牌立即失效。**没有独立的“集成账号”或只读令牌**，MCP 实际拥有签发超管的全部权限。
- **权限校验与 REST 是同一套**：MCP 调用的是同一批领域服务，因此同样走 `_require` 和数据范围（`mcp/crud_service.py:276-303`；`mcp/server.py:209-236`）。不是第二套权限模型。
- **没有工具级 scope**：令牌只有一个 `erp:crud` 范围，不能“只给产品只读”。全局启用开关也是全有或全无。
- 删除是软删除，要求显式 `confirm=true`；无调用频率限制、无来源 IP 限制、无 MCP 调用审计（审计里只能看到“某用户改了产品”，看不出是 MCP 改的）。

### 6.5 审计日志

审计写入是事务内的，失败会跟随业务一起回滚（`system/audit_logs/recorder.py:11-32`）。覆盖面按模块看是“审批链覆盖、登记链缺失”：

| 有审计 | 没有审计 |
|---|---|
| 基础资料：产品、客户、供应商、合作伙伴 | 单证主体 |
| 采购合同、销售报价、销售合同、出货明细 | 采购询价、开票通知、跟单节点 |
| 样品寄样 | 打样申请、样品登记 |
| 入库单、出库单、盘点单 | 入库计划、出库计划 |
| 付款申请、付费申请、报销 | 收款/认领/分摊、核销单、退税、结算、杂费、口岸数据 |
| — | QC 查验、组织与权限、登录/登出、MCP 开关与令牌、工作台待办/日程/公告 |

页面侧：

- 只有 `system:super_admin` 能查询和导出（`audit_logs/services.py:25-73`），没有“只读审计员”角色。
- 筛选条件 `action` / `resource_type` 是前端硬编码枚举（`system/AuditLogsPage.tsx:23-50`），新增模块不会自动出现。
- 记录的是“谁、在什么时间、对哪张单做了什么动作、摘要”，绝大多数调用不传 `payload`，**没有变更前后值**，无法还原金额或字段改动。
- 登录失败、越权尝试、权限变更、MCP 令牌签发这类最该审计的动作全部没有埋点。

### 6.6 工作台与四个子页

工作台本身有侧边栏菜单（`/`，`dashboard:view`）；四个子页都不在侧边栏，统一挂在 `/workspace/*`，`menuPath` 指回 `/`。

**聚合来源**（`system/dashboard/services.py:89-150`；`business_task_repositories.py:82-303`）：

| 区块 | 数据来源 | 过滤规则 |
|---|---|---|
| 人工待办 | `dashboard_todos` 表 | 指派给我 + 我创建的 |
| QC 待办 | QC 查验任务 | `assignee_user_id = 我`；超管看全部 |
| 跟单待办 | 跟单计划节点 | 同上（按负责人） |
| 入库审批 | 入库单 `submitted` | 审批人=我；超管看全部 |
| 其他审批 | 出口合同、采购合同、报价、出货、付款、付费、报销、寄样、出库单共 9 类 | 审批人=我；超管看全部 |
| 通知 | `notifications` 表 | `user_id = 我` |
| 日程 | `dashboard_schedules` 表 | `user_id = 我`，**不过滤日期** |
| 公告 | 已发布公告 | 全部可见 |
| 快捷入口 | `dashboard_shortcuts` 表 | `user_id = 我` |

由此产生的工作台口径：

- **待审批不是按数据范围，而是按“审批人字段 = 我”**。主管即使 `data_scope=department`，也看不到本部门别人名下的待审批；只有超管因为走“全部分支”才能看全。这和列表页的可见范围是两套规则。
- **新盘点单没有接入工作台**：盘点审批既不进待审批聚合，也不发通知，只能在盘点页自己找。入库计划、出库计划、开票通知同样没有待办。
- **`today_schedule_count` 名不副实**：统计的是该用户全部日程条数（`:147`），前端标签写“今日日程”（`zh-CN.json:242`），历史日程越多数字越大。
- **没有第二套金额口径**：工作台不展示应收/应付/利润，因此不存在和第五章三套报表冲突的第四个金额来源；冲突只在“谁算待办”这一层。
- **`/dashboard` 全量返回**：该用户的全部通知、全部日程、全部快捷入口一次性返回，没有分页或上限；铃铛未读数虽然准确，但依赖这份全量列表（`dashboard/repositories.py:97-150`、`:226-232`）。

**通知与提醒**（`dashboard/notification_writer.py:19-30`、`:71-202`；`notifications/reminders.py:21-107`）：

- 审批类通知只覆盖 10 类资源：销售合同、采购合同、报价、出货、付款、付费、报销、寄样、出库单、入库单；提交给指定审批人时写入，审批/驳回时通知提交人。
- 定时提醒只有两类：QC 任务临近/逾期、跟单节点逾期；由后台任务按天扫描。
- 收款、核销、退税、结算、盘点、杂费没有任何通知或提醒。
- 通知没有实时推送或轮询，铃铛只在打开时刷新。

### 6.7 顶栏铃铛与快捷入口

- **铃铛**：显示未读数（来自 `/dashboard` 的 `unread_notification_count`）与前 5 条预览（`components/topbar/NotificationBell.tsx:9`、`:28`、`:36-37`）。点条目会先检查目标路径是否在当前用户菜单里，不在则退回通知列表页（`:102-123`）。通知页支持单条已读、全部已读、删除，删除按 `user_id` 隔离。
- **快捷入口**：新建时“目标页面”选项来自当前用户可见菜单，附带 3 个固定带查询参数的预设（提交后的合同/报价/出货）（`pages/dashboard/shortcutCatalog.ts:88-115`）。入口按用户隔离，可删。
- **后端不校验快捷入口的目标路径**：`create_shortcut` 只做长度/枚举校验，不校验该路径是否属于该用户菜单，也不限制条数（`dashboard/services.py:355-382`）。前端只在点击时拦截（`DashboardShortcutsPanel.tsx:51-61`），因此可以存下永远打不开的入口。
- **公告发布仍只认超管**：后端写死 `_can_create_announcement` 检查 `system:super_admin`（`api/v1/dashboard.py:123-136`），前端同样只认超管（`pages/helpers/permissions.ts:5-7`）；`announcement:create` 权限码存在但无人读取。日程创建也没有读取 `schedule:create`，任何登录用户都能建自己的日程。

### 6.9 本章结论

- **权限怎么落到菜单和路由**：角色挂权限码 → 菜单按权限码精确过滤 → 前端用 `menuPath` 判断可访问性 → 接口由服务层 `_require` 最终拦截。菜单只是可见性，不是授权；数据范围主要靠角色 `data_scope` 字段，只有 QC/跟单把 `view_all` 权限码当作例外通道。
- **组织/部门现在被谁用**：只被 `data_scope = department / department_tree` 使用，用于列表与单据可见性；不参与审批路由、待办分配和报表分组。演示角色全是 `all`，所以默认部署下部门对数据零影响。公司信息只影响打印。
- **MCP 暴露了什么**：3 类资源 15 个工具；鉴权是独立的 Bearer 令牌，但权限与数据范围复用 REST 的同一套服务，不是第二套模型。问题在令牌身份——只能由超管签发且继承其全部权限，没有只读或工具级 scope。
- **审计边界**：审批链基本覆盖，登记链大量缺失；组织/权限、登录、MCP、财务登记类动作都没有埋点，也没有变更前后值。它目前更像“关键单据动作日志”，不是合规审计。
- **工作台有没有第二套口径**：金额上没有（工作台不展示钱），但“待办/待审批”有第二套口径——按审批人字段聚合而非数据范围，且漏掉盘点与计划类单据；`today_schedule_count` 也不是“今日”。
- **铃铛和快捷入口的实际范围**：铃铛只覆盖 10 类审批与 2 类提醒，按人隔离、打开时刷新；快捷入口按人隔离、目标来自菜单，但后端不校验路径与数量。两者都可用，但都不是“全量待办/全量消息”的入口。
