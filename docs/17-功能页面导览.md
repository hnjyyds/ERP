# 功能页面导览

> 本文档用于逐页向用户讲解系统功能。第一批只做「全景清单」，逐页展开（用途、使用角色、列表列、表单字段、动作与状态流转、接口与表、已知局限）在清单确认后另起章节。
>
> 口径：以 `frontend/src/app/routes.ts` 的 `routeDefinitions` 为唯一路由依据；权限码取后端种子菜单 `backend/app/modules/system/auth/seed_navigation.py` 的 `required_permission`；菜单顺序取该文件的 `sort_order`，分组取 `frontend/src/app/routes.ts` 的 `navGroup` 与 `frontend/src/app/components/sidebar/sidebarNavigation.ts` 的分组顺序。状态结论来自对页面组件、页面注册表和实际操作入口的核对。

## 0. 核对结论摘要

- `routeDefinitions` 共 **41 条**路由；`pageRegistry` 有 **41 个**渲染器，**没有缺失渲染器的路由**。
- 后端种子菜单共 **37 条**菜单路径，全部能命中 `routeDefinitions`；剩余 **4 条**为工作台子页，不在侧边栏。
- 41 条路由中：完整可用 **35** 条；只有列表无详情 **1** 条；只读展示 **5** 条；空壳 **0** 条；整页级「有接口无入口」**0** 条。
- 所有带 `detailRoot` 的页面，详情路径都由根路径派生，不在 `routeDefinitions` 中单独注册；下文在「路由」列以 `{id}` 标出。

## 3. 代码里存在但用户看不到的页面

结论：**`routeDefinitions` 内没有完全无入口的页面。** 具体边界如下：

1. **不在侧边栏、但有站内入口的 4 个工作台子页**：待办、日程、通知、公告。
   - 工作台卡片/面板可跳转：`dashboard/DashboardPage.tsx:356-375`、`dashboard/views/DashboardOverviewPanels.tsx:63-278`。
   - 通知另有顶栏铃铛入口（`frontend/src/app/components/topbar/NotificationBell.tsx`）。
2. **不在 `routeDefinitions` 的两个状态页**（不属于业务菜单，但用户会看到）：
   - 登录页 `/login`：`frontend/src/app/pages/auth/LoginPage.tsx`，由 `frontend/src/app/App.tsx:258` 在未登录时渲染。
   - 无权限页 `AccessDeniedPage`：由 `frontend/src/app/components/router/AppRouter.tsx:7-9,38-55` 在无权访问时渲染，组件位于 `reporting/ReportingPage.tsx`。
3. **共用基座组件不是独立页面**：`masterdata/TradingPartnerPage.tsx` 被客户、工厂、合作伙伴三个页面复用，没有自己的路由。
4. **未发现孤儿页面**：所有 `pages/**/*Page.tsx` 要么在 `pageRegistry` 中注册，要么是上述共用基座/登录页；没有「组件存在但既无菜单也无站内跳转」的业务页面。

## 4. 菜单里有但点进去是空壳的页面

结论：**本轮核对为 0 个。**

依据：后端种子菜单 37 条路径全部命中 `routeDefinitions`；`routeDefinitions` 的 41 条路由全部命中 `pageRegistry` 的页面渲染器（41/41）；页面代码中没有「开发中」「敬请期待」「暂未开放」等占位文案。

但以下 5 个页面是**轻量或只读视图**，容易被误认为空壳，讲解时需要提前说明：

| 页面 | 实际内容 | 为什么容易被误判 |
|---|---|---|
| 25 财务摘要 `/finance` | 关键金额摘要 + 财务模块导航卡片 | 没有列表和表单，看起来像入口页 |
| 26 经营总览 `/finance/overview` | 经营指标汇总与趋势 | 纯展示，无写操作 |
| 35 财务报表 `/finance/reports` | 多类报表、筛选、下钻、CSV 导出 | 只有查询与导出 |
| 36 老板看板 `/reporting` | 审批聚合、统计与跳转处理 | 只有聚合查询 |
| 5 公告 `/workspace/announcements` | 已发布公告只读列表 | 无新增/编辑入口（发布在工作台） |

## 5. 命名与入口注意事项

## 第一章 基础资料

### 1.0 先统一两个口径

- 菜单「**工厂资料**」就是**供应商**（`/masterdata/suppliers`，表 `suppliers`）。系统里没有独立的「工厂」实体，工厂、外发加工厂都按供应商登记。
- 菜单「**订单中心**」就是**出口合同**（`/sales/contracts`，表 `export_contracts`），不是所有订单的总入口。采购合同在另一页。
- 本章及后续章节统一称「供应商」「出口合同」。

### 1.1 五类主数据一览

| 主数据 | 页面 | 主表 | 下游怎么引用 | 删除方式 |
|---|---|---|---|---|
| 产品 | 产品资料 | `products` + `product_accessories` | 逻辑 ID + 产品编码/名称/规格/型号/单位快照 | 软停用；配件物理删除 |
| 供应商 | 工厂资料 | `suppliers` + 联系人 + 信用档案 | 逻辑 ID + 供应商名称快照 | 软停用；联系人物理删除 |
| 客户 | 客户资料 | `customers` + 联系人 + 信用档案 | 逻辑 ID + 客户名称快照 | 软停用；联系人物理删除 |
| 合作伙伴 | 合作伙伴 | `partners` + 联系人 | 逻辑 ID + 伙伴名称/类型快照 | 软停用；联系人物理删除 |
| 单证资料 | 单证资料 | `document_parties` | **没有任何下游引用** | 软停用；停用时清默认标记 |

### 1.2 贯穿全章的共性结论

这五类主数据在系统里的接入方式是统一的，先讲共性，后面每类只讲差异。

1. **主数据内部是真外键，业务单据不是。** 联系人、信用档案、产品配件都通过数据库外键挂在主表上（`backend/app/modules/masterdata/customers/models.py:38`、`suppliers/models.py:38`、`partners/models.py:38`、`products/models.py:48`）。但报价行、合同行、出货行、出入库单、付款单引用主数据时，全部是普通 `String(36)` 字段加名称快照，没有数据库外键。数据库层不会阻止写入一个不存在的主数据 ID。
2. **后端创建单据时基本不校验主数据。** 出口报价、出口合同、采购合同、收款、付款、出货等接口，直接把前端传来的 `customer_id`/`customer_name`/`supplier_id`/`supplier_name` 落库（例如 `sales/contracts/services.py:83-99`、`purchase/contracts/services.py:107-108`、`finance/receipts/models.py:22-23`）。是否存在、是否停用，不校验。只有三处例外：费用发票创建时会校验合作伙伴名称/类型/状态（1.6）、从出口合同生成采购合同时会按产品 ID 或编码回查产品与配件（1.3）、打印/导出会实时回读主数据（下一条）。
3. **删除一律是软停用。** 五个 `DELETE` 端点都只把 `status` 改为 `inactive`，没有任何引用检查，也不联动停用下游（`products/services.py:161-177`、`customers/services.py:270-292`、`suppliers/services.py:266-288`、`partners/services.py:246-265`、`document_parties/services.py:185-200`）。联系人、产品配件是物理删除。
4. **列表过滤口径不一致。** 产品列表默认只返回 `active`，停用产品会从产品页和所有下拉里消失（`products/repositories.py:515-529`）；客户、供应商、合作伙伴、单证资料不传 `status` 时返回全部，**停用记录仍会出现在下拉里**。
5. **下拉是一次性加载，默认 50 条，无远端搜索。** 出口合同、采购合同的客户/供应商/产品下拉都是一次 `list...()` 调用（`sales/hooks/useExportContractOptions.ts:25-52`、`purchase/hooks/usePurchaseContractOptions.ts:23-45`），后端默认 `limit=50`。超过 50 条的主数据在后两个页面选不到。
6. **唯一会实时回读主数据的地方是打印/导出。** 出口合同打印会实时读客户主联系人（`system/printing/services.py:206-220`）；采购合同模板会实时读供应商地址与主联系人电话/邮箱（`printing/services.py:243-260`），并按 `product_id` 实时读产品图片和包装说明（`printing/services.py:262-287`）。其余页面全部看快照。

### 1.3 产品（`products` / `product_accessories`）

#### 关键字段

| 字段 | 业务作用 |
|---|---|
| `code` | 唯一编码。除展示外，还被「从出口合同生成采购合同」用作回查商品的锚点 |
| `cn_name` / `en_name` | 中英文品名，写入所有下游行快照 |
| `specification` / `model` | 规格、型号，写入下游行快照 |
| `customs_code` | 海关编码，仅主数据登记与列表搜索使用 |
| `tax_rate` / `rebate_rate` | 增值税率、出口退税率。**当前不参与任何计算** |
| `package_info` | 包装说明。采购合同模板打印时会拼进行备注 |
| `unit` | 单位，写入下游行快照 |
| `image_url` | 产品图片。采购合同模板打印时实时读取 |
| `status` | `active` / `inactive` |
| 配件：`accessory_name`、`unit_consumption`、`unit`、`default_supplier_name`、`purchase_split_rule` | 采购合同生成时按「成品数量 × 单耗」展开成采购行；`default_supplier_name` 只是文本，不指向供应商表 |

#### 引用方式

- **下游全部是快照。** 报价行、出口合同行、出货行、库存、出库行、采购合同行、询价行、样品行、QC 行都存 `product_id`（普通 String）+ `product_code`/`product_name`/`specification`/`model`/`unit`（`sales/contracts/models.py:87-94`、`sales/quotations/models.py:62-68`、`sales/shipments/models.py:77-83`、`warehouse/outbound_orders/models.py:71-74`、`purchase/inquiries/models.py:44-46`）。
- **会实时读产品表的三处：**
  1. 从出口合同生成采购合同时，按 `product_id` 读配件；行上没有 `product_id` 时，退化为按 `product_code` 回查（`purchase/contracts/services.py:562-622`）。
  2. 采购合同模板打印，按 `product_id` 读 `image_url` 和 `package_info`（`printing/services.py:262-287`）。
  3. 产品详情「交易记录」和「相关客户」，按 `product_id` 聚合报价、采购、出货、出口合同行（`products/repositories.py:230-259`、`:261` 起）。

#### 改动的影响

| 改动 | 历史单据 | 未结单据 | 打印/导出 |
|---|---|---|---|
| 改中英文名、规格、型号、单位 | 不变，显示旧快照 | 不变；列表和详情都读快照 | 出口合同打印不变；采购模板只读图片和包装，不读名称 |
| 改 `code` | 不变 | 不变；但若从出口合同生成采购合同时行上没有 `product_id`，按新编码回查会失败，报「商品编码 xxx 未关联商品资料」 | 不变 |
| 改 `package_info` | 不变 | 不变 | **采购合同模板下次打印会用新包装说明** |
| 改 `image_url` | 不变 | 不变 | **采购合同模板下次打印会用新图片** |
| 改 `tax_rate` / `rebate_rate` | 无影响 | 无影响 | 无影响；系统里没有计算读取这两个字段，退税额来自核销单，不来自产品 |
| 改配件（增删改） | 不变 | 不变 | 从出口合同生成采购合同时按**当前**配件重算，已生成的采购合同不重算 |

#### 停用与删除

- 产品停用是 `status="inactive"`，无引用拦截（`products/services.py:161-177`）。
- 停用后：产品页看不到（列表默认过滤 active），出口合同/采购合同/报价的下拉也选不到。
- 停用后：历史单据和未结单据照常显示快照；采购合同模板仍能按 `product_id` 读到停用产品的图片和包装（`get_product` 不判断状态）。
- 配件是物理删除（`products/repositories.py:199-216`），删掉后无法从出口合同再生成含该配件的采购行。

#### 使用面

| 页面 / 服务 | 用途 |
|---|---|
| 产品资料页 | 主数据增删改查、图片、配件、导入导出、交易记录 |
| 出口报价 | 产品下拉；行快照；「历史采购参考价」按 `product_id` 查旧报价行 |
| 出口合同 | 产品下拉；行快照；详情/交易记录按 `product_id` 聚合 |
| 采购合同 | 产品下拉；按配件生成采购行；模板打印读图片和包装 |
| 采购询价 | 询价行快照 |
| 样品申请 / 样品登记 | 产品快照 |
| QC 查验 | 查验行 `product_id`/`product_code`/`product_name` 快照 |
| 入库计划 / 入仓 / 出库计划 / 货物出库 | 产品快照；库存表另存 `code`/`name`/`unit` |
| 出货明细 | 出货行快照 |

#### 已知局限

- **没有价格字段。** 报价单价、合同单价、采购单价全靠手填；「历史采购参考价」只能反查旧报价行里手填的 `purchase_reference_price`，不是产品主数据能力。
- **税率、退税率是死字段。** 登记后没有任何计算、校验或报表引用，不能支撑「按产品算退税」。
- **配件默认供应商是纯文本。** 不指向 `suppliers`，供应商改名不联动，也无法按供应商汇总配件需求。
- **产品编码可修改，且生成采购合同时会用编码回查。** 一旦历史合同行没有 `product_id`，改编码就会断链。
- **停用不做引用拦截。** 停用后历史采购合同打印仍会带出该产品的图片和包装。
- **下拉上限 50 条且无搜索。** 产品超过 50 个时，出口合同和采购合同页面选不到后面的产品。
- **删除配件无引用检查。** 已生成的采购合同不会追溯，但后续再生成会少行或直接报错。

#### 停用与删除

- 停用后：客户资料列表仍能看到；报价页、出口合同页的客户下拉 `listCustomers()` 默认不带 `status`，**停用客户仍可被选中新建单据**。
- 停用后：历史单据、未结单据、打印都照常。
- 联系人物理删除。

#### 使用面

| 页面 / 服务 | 用途 |
|---|---|
| 客户资料页 | 主数据增删改查、联系人、信用档案、交易记录 |
| 出口报价 | 客户下拉；表头快照 |
| 出口合同 | 客户下拉；表头快照；打印实时读联系人 |
| 出货明细 | `customer_id`/`customer_name` |
| 出库计划 / 货物出库 | `customer_id`/`customer_name` |
| 收款管理 | 手填 `customer_id`/`customer_name` 快照 |
| 核销退税 / 杂费 / 口岸数据 | 客户名称文本 |
| 单证资料 | `customer_id` + `customer_name` 快照 |
| 产品资料详情 | 按出口合同行的 `product_id` 聚合，再按合同 `customer_id` 汇总客户 |

#### 已知局限

- **没有客户地址、联系人快照。** 出口合同打印不含地址；客户地址后来改了，也无从追溯当时用的是哪个地址。
- **创建单据不校验客户存在与启用。** 可以写入不存在的 `customer_id`，也可以给停用客户下新合同。
- **信用额度、付款条件不参与控制。** 不能做信用额度占用、超额拦截；合同付款条件与客户信用档案没有关联。
- **首付/预收款与客户主数据无关联。** 合同预收款只存 `payer_name` 文本。
- **停用客户仍出现在下拉里。**
- **客户交易记录只聚合出口合同和出货计划。** 不含收款、核销、杂费，不是完整应收台账。

### 1.6 合作伙伴（`partners`）

#### 关键字段

| 字段 | 业务作用 |
|---|---|
| `code` | 唯一编码 |
| `cn_name` / `en_name` | 伙伴名称，写入费用发票与付费申请快照 |
| `partner_type` | 快递 `express`、货代 `freight_forwarder`、保险 `insurer`、承运 `carrier`；写入费用单据快照，并参与财务总览统计 |
| `country` / `address` / `website` | 仅主数据展示，下游不快照 |
| 联系人 | 仅主数据展示；费用单据不引用 |
| `status` | `active` / `inactive` |

#### 引用方式

- 费用发票 `PartnerFeeInvoice`：`partner_id`（普通 String）+ `partner_name` + `partner_type` 快照（`finance/fee_payments/models.py`）。
- 付费申请 `FeePaymentRequest`：同上。
- 财务总览按 `partner_type` 统计启用伙伴数（`finance/overview/repositories.py:134-152`）。
- 财务报表按 `partner_name` 文本筛选（`finance/reports/repositories.py:434-435`）。
- 伙伴详情「交易记录」按 `partner_id` 聚合费用发票与付费申请（`partners/repositories.py:335-365`）。

#### 改动的影响

| 改动 | 历史单据 | 未结单据 | 说明 |
|---|---|---|---|
| 改名称 | 显示旧快照 | 显示旧快照 | 但新建费用发票时，后端会校验 `partner.cn_name == 提交的 partner_name`，改名后前端若仍带旧名会报「合作伙伴名称不一致」（`fee_payments/services.py:290-291`） |
| 改 `partner_type` | 不变，存旧类型 | 不变 | 新建时同样会校验类型一致（`fee_payments/services.py:292-293`） |
| 改地址 / 网站 / 联系人 | 无影响 | 无影响 | 费用单据不含这些字段，也没有打印模板读取 |
| 改银行信息 | 无此项 | 无此项 | 合作伙伴表没有银行账号字段 |

#### 停用与删除

- 停用是 `status="inactive"`，无引用拦截（`partners/services.py:246-265`）。
- 费用发票创建时会校验 `partner.status == "active"`，停用后**不能新登记**费用发票（`fee_payments/services.py:294-295`）；但只有填了 `partner_id` 才走这段校验。
- 历史费用单据、付费申请、财务统计都不受影响。
- 联系人物理删除。

#### 使用面

| 页面 / 服务 | 用途 |
|---|---|
| 合作伙伴页 | 主数据增删改查、联系人、交易记录 |
| 付费管理（费用发票） | `partner_id`/`partner_name`/`partner_type`，可关联出货单 |
| 付费管理（付费申请） | `partner_id`/`partner_name`/`partner_type` |
| 财务摘要 / 经营总览 | 按类型统计启用伙伴数 |
| 财务报表 | 按伙伴名称文本筛选费用 |

#### 已知局限

- **付费表单里 `partner_id` 是手填文本框，不是下拉。** 不填 `partner_id` 也能建费用发票，此时完全不校验伙伴主数据（`finance/forms/feeForms.tsx:23-25`、`FeesView.tsx:283-290`）。
- **出货单没有货代/承运/保险字段。** `ShipmentPlan` 只有 `shipping_method`、`vessel_name`、`container_no`、`booking_no` 等文本，不能结构关联合作伙伴，因此无法按货代统计某票出货的应收应付。
- **没有银行账号、SWIFT。** 付费只能手填 `payment_account`。
- **联系人完全没被使用。** 费用单据不取伙伴联系人，也没有对账单打印。
- **伙伴停用只拦「填了 partner_id」的新费用发票。** 不填 ID 的纯文本费用单照样能建。

### 1.7 单证资料（`document_parties`）

#### 关键字段

| 字段 | 业务作用 |
|---|---|
| `code` | 唯一编码 |
| `party_type` | 收货人 `consignee`、通知人 `notify_party`、开证行 `issuing_bank`、账单通知人 `bill_notify_party` |
| `display_name` | 单据上显示的主体名称 |
| `customer_id` / `customer_name` | 归属客户；ID 是普通 String，名称是快照 |
| `country` / `address` / `contact_person` / `email` / `phone` | 单证收件信息 |
| `bank_name` / `swift_code` / `account_no` / `tax_id` | 开证行等银行信息 |
| `is_default` | 同一 `party_type` + `customer_id` + `owner_user_id` 下只能有一个默认（`document_parties/repositories.py:67-72`、`:160`） |
| `status` | `active` / `inactive` |

#### 引用方式

**目前没有任何下游业务引用它。** 全后端搜索 `document_party`/`DocumentParty`，只命中本模块、菜单种子和权限种子（`masterdata/document_parties/*`、`system/auth/seed_navigation.py`、`seed_permissions.py`）。出口合同、出货明细、报关、财务都没有指向单证资料的字段，也没有任何页面读取它自动带出收货人/通知人/开证行。

#### 改动的影响

- 改名称、地址、联系人、银行账号：**不影响任何业务单据**，因为没有引用。
- 反过来也成立：在这里维护得再完整，出口合同和出货单也不会自动带出。
- `customer_id` 不是外键，客户改名不会改这里的 `customer_name` 快照，也不会反向影响客户。

#### 停用与删除

- 停用是 `status="inactive"`，无引用拦截；停用时强制 `is_default=False`（`document_parties/repositories.py:176-184`）。
- 列表不传 `status` 时仍会显示停用记录；`lookup` 接口用 `active_only=True`，只返回启用记录。
- 没有物理删除入口，只有停用。

#### 使用面

| 页面 / 接口 | 用途 |
|---|---|
| 单证资料页 | 列表、筛选（类型/客户/状态）、详情、新增/编辑/停用 |
| `GET /document-parties/lookup` | 后端已实现按类型 + 客户查启用记录，**前端没有调用点** |
| 其余业务页面 | 无 |

#### 已知局限

- **是一个孤立的主数据库。** 出口合同、出货、单证打印都没有接它，维护后不产生任何业务效果。
- **`lookupDocumentParties` 没有前端调用点。** 前端 API 已封装（`frontend/src/api/masterdata-partners.ts:258-265`），但只有单证资料页自己用 `listDocumentParties`。
- **`customer_id` 是普通 String。** 不能保证归属客户存在，也不能级联。
- **默认标记只在「类型 + 客户 + 创建人」范围唯一。** 换一个业务员看不到别人建的默认单证资料，同一客户可能有多套默认。
- **停用不拦截。** 因为没人引用，所以也谈不上拦截；但也意味着停用不会带来任何业务变化。

### 1.8 本章结论

基础资料这一层目前是「**主数据可维护，业务单据靠快照**」的形态：

- 好处是历史单据不会被主数据改名改价直接影响，账面临时改动风险低。
- 代价是：主数据改了不会回写历史，也不会强制新单据使用最新值；数据一致性完全依赖前端下拉和人工操作。
- 最明显的三个缺口：**没有任何引用拦截、客户/供应商信用额度完全不参与业务控制、单证资料是孤立数据**。
- 进入下一章（报价）时，需要特别记住：报价行的产品信息是快照，客户名称是快照，采购参考价是手填文本；报价不会因为产品主数据或客户主数据后续变化而自动更新。

## 第二章 报价 → 样品 → 出口合同

### 2.1 这条主线在系统里的真实走法

```
客户询价
  ├─ 出口报价：草稿 → 待审批 → 已审批 ──「生成出口合同」──► 出口合同（草稿）
  └─ 打样管理：草稿 → 已发送 → 进行中 → 已完成 ──「载入样品登记」──► 样品登记
                                                              └─► 寄样单：草稿 → 待审核 → 已审核 → 已寄出
出口合同：草稿 → 待审批 → 已审批 ──► 出货明细 / 采购合同 / 收款核销
```

| 衔接 | 系统里是否“一键” | 依据 |
|---|---|---|
| 报价 → 出口合同 | **是**。已审批报价点「生成出口合同」，生成草稿合同并写 `source_quotation_id/no`，报价状态变「已生成合同」 | `sales/quotations/services.py:370-460` |
| 打样申请 → 样品登记 | **是**。打样「已完成」后可点「载入样品登记」；同一申请只能转一次 | `sample/requests/services.py:294-314` |
| 样品登记 → 寄样单 | **半自动**。寄样行必须填样品标识，但不会从样品登记带出；审核时按样品留样量扣减 | `sample/deliveries/services.py:605-642` |
| 报价 ↔ 寄样 | **弱关联**。寄样单的报价号是手填文本；报价详情的「寄样关联」按「客户 + 首个产品」反查已审核/已寄出的寄样单，不按 `quote_id` | `sales/quotations/services.py:500-522` |
| 报价 ↔ 打样 | **无关联**。打样申请没有报价字段，需要人工另建 | `sample/requests/models.py:15-60` |

一句话：**报价到合同是硬衔接，样品内部是硬衔接，报价到样品基本靠人。**

### 2.2 出口报价（`/sales/quotations`）

#### 页面与数据

| 项 | 内容 |
|---|---|
| 菜单 / 路由 | 「出口报价」/ `/sales/quotations`（`frontend/src/app/pages/sales/ExportQuotationsPage.tsx:18-79`） |
| 主表 / 行表 | `export_quotations` / `export_quotation_lines`（`backend/app/modules/sales/quotations/models.py:15-87`） |
| 权限 | 查看 `sales:quotation:view`、编辑 `sales:quotation:edit`、审批 `sales:quotation:approve`、导出 `sales:quotation:export` |
| 指标卡 | 报价单总数、待审批数、已审批数、报价总额（`ExportQuotationListPanel.tsx`） |
| 列表列 | 报价单号、状态、客户、贸易条款、金额、已生成合同号、详情入口 |
| 筛选 | 关键字（单号/客户/贸易条款/产品）、状态、客户（服务端搜索） |

状态筛选**没有「已退回」选项**（`ExportQuotationListPanel.tsx:47-48`），被驳回的报价只能在列表里按客户/关键字找，不能按状态筛。

#### 状态机

| 当前 | 动作 | 结果 | 条件与限制 |
|---|---|---|---|
| 草稿 | 提交审批 | 待审批 | 必须指定审批人，且审批人不能是提交人；审批人要有 `sales:quotation:approve` |
| 待审批 | 审批通过 | 已审批 | 只有被指定的审批人（或有全局审批权的管理员）能操作（`sales/quotations/services.py:250-284`） |
| 待审批 | 驳回 | 已退回 | 必须填驳回原因（`sales/quotations/services.py:286-326`） |
| 待审批 | 撤回 | 草稿 | 仅提交人本人或超管；已生成合同的不能撤回（`sales/quotations/services.py:328-368`） |
| 已审批 | 生成出口合同 | 已生成合同 | 确认日期必填；生成草稿合同；重复点击会被后端拒绝（`sales/quotations/services.py:370-409`） |
| 已退回 | 重新编辑 | 草稿（保存时） | 只有草稿/已退回能载入编辑（`sales/quotations/services.py:124-168`） |

#### 新建与编辑表单

| 字段 | 说明 |
|---|---|
| 报价单号 | 保存后自动生成，页面只读 |
| 报价日期 / 有效期至 | 有效期会优先成为生成合同的「计划出运日」 |
| 客户 | 服务端搜索、只返回启用客户；选中后带出客户名称、币种、贸易条款 |
| 客户名称 | 只读快照 |
| 销售员 | **手填文本**，不是员工下拉；新建时不提交 `sales_user_id`，编辑旧单沿用原 ID |
| 币种 / 贸易条款 / 说明 | 文本 |
| 明细 | **页面只支持一行**：商品标识、产品编号、产品名称、规格、型号、数量、单位、单价、运费方式、运费、采购参考供应商、采购参考价、行备注 |

录入规则与校验：

- 行金额 = 数量 × 单价；**报价总额 = 各行（金额 + 运费）**（`sales/quotations/services.py:552-579`）。
- 数量必须 > 0，单价必须 > 0，运费金额不能为负。
- 客户名称必填；一旦选择客户（传 `customer_id`），服务端校验其存在且启用（不存在 422，停用 409）；不选客户、只填名称时不做主数据校验。
- 销售员名称不校验；新建时没有 `sales_user_id`，编辑旧单会原样回传原 ID（若该员工后来停用，只要 ID 未变仍可保存）。
- 行里的「商品标识」是手填 `product_id`：留空不校验；一旦填写，必须是真实且启用的产品 ID，否则 422。产品编号/名称不校验。
- 只有草稿、已退回可以载入编辑；待审批、已审批、已生成合同都只读。

#### 详情页区块

- 表头：状态、客户、销售员、贸易条款、审批人、有效期、已生成合同号、说明、驳回原因。
- 合同行：产品编号/名称、规格/型号、数量、单位、单价、金额、运费、行备注。
- 历史报价：同一客户 + 同一产品的历史报价对比（`sales/quotations/services.py:462-478`）。
- 采购参考：按行产品汇总的历史采购价参考（`sales/quotations/services.py:479-499`）。
- 寄样关联：同客户 + 首个产品的已审核/已寄出寄样单（`sales/quotations/services.py:500-522`）。
- 操作：载入编辑、提交审批、审批、驳回、撤回、导出 PDF、生成出口合同。

#### 报价转合同时复制什么

`sales/quotations/services.py:411-460` 的复制口径：

| 合同字段 | 来源 |
|---|---|
| 合同日期 | 生成时填的确认日期 |
| 客户 / 客户名称 | 报价的客户与快照 |
| 销售员 | 报价的 `sales_user_id/name` |
| 币种 / 贸易条款 | 报价 |
| 计划出运日 | 报价有效期；没有有效期时用确认日期 |
| 付款条件 | **空字符串**，需要后续在合同里补 |
| 备注 | 报价说明 |
| 明细 | 产品、规格、型号、数量、单位、单价、金额、备注 |

**不复制**：运费方式/运费、采购参考价。因此报价总额（含运费）与合同总额（只含货款）通常不相等。

#### 已知局限

- **页面只能维护一行明细。** 后端 `lines` 是数组，但新增/编辑表单固定只提交一行（`exportQuotationHelpers.tsx:186-205`）。
- **商品标识、销售员是手填文本。** 商品标识填错会被新校验以 422 拒绝；销售员名称与员工账号没有关联。
- **已生成合同后仍能点「生成出口合同」。** 按钮在「已审批/已生成合同」都显示，第二次点击后端报「只有已审批报价可以生成出口合同」；没有幂等键（进入第二批）。
- **状态筛选缺「已退回」**（`ExportQuotationListPanel.tsx:47-48`）。
- **没有打印模板。** 报价只能导出 PDF/CSV，不读取客户地址、联系人和单证资料。

### 2.3 打样管理（`/sample/requests`）

#### 页面与数据

| 项 | 内容 |
|---|---|
| 路由 | `/sample/requests`（`frontend/src/app/pages/sample/SampleRequestsPage.tsx`） |
| 表 | `sample_requests` + 明细 `sample_request_lines` + 进度 `sample_request_progress` + 费用 `sample_request_fees`（`sample/requests/models.py:15-118`） |
| 权限 | 查看 `sample:request:view`、编辑 `sample:request:edit`、费用 `sample:request:fee:edit`、导出 `sample:request:export` |
| 指标 | 打样单数、进行中数、进度条数、费用条数 |
| 列表列 | 单号、状态、客户、产品、供应商、去向、要求交期、详情 |

#### 状态与进度

- 申请状态：草稿、已发送、进行中、已完成、已取消。
- 进度只能**向前**：草稿 < 已发送 < 进行中 < 已完成；状态不能回退（`sample/requests/services.py:423-424`）。
- 要置为「已完成」，必须同时满足：进度状态选「已完成」、阶段选「客户确认」、申请当前已是「进行中」（`sample/requests/services.py:418-422`）。
- 已取消的申请不能更新进度；进度也不能把申请改成已取消（`sample/requests/services.py:414-417`）。
- **没有「取消申请」接口**：新建时状态只能选草稿/已发送/进行中，之后也没有任何入口能把申请改成「已取消」。

#### 新建表单

| 字段 | 说明 |
|---|---|
| 客户标识 / 客户名称 | **手填文本**，不校验客户主数据 |
| 产品编号 / 产品名称 | **手填文本**，不校验产品 |
| 供应商 | 手填名称 |
| 打样去向 | 内部打样 / 外发工厂 |
| 要求交期、要求说明 | 文本 |
| 明细 | 产品编号/名称、数量、单位、要求；数量必须 > 0 |

创建后可做的事只有：加进度、登记费用、费用转付款申请、完成后转样品登记、打印内部打样单。**不能改客户/产品/明细，也不能删除。**

#### 费用与付款

- 费用类型：打样费、快递费、材料费；承担方是供应商/合作伙伴/员工，付款对象是**手填名称**。
- 「申请付款」会在财务生成一张费用发票 + 一张付费申请，审批人必须有财务查看权限且不能是申请人（`sample/requests/services.py:227-292`）。
- 每次点击都会新建一组发票/申请，**没有防重复**（留待第二批幂等处理）。

#### 转样品登记

- 仅「已完成」的打样单可转，且只能转一次；重复转会报「该打样单已生成样品登记」（`sample/requests/services.py:294-314`）。
- 转的时候要选样品分类、状态、收样日期、数量、单位、描述等；产品/客户/供应商从打样单复制。

### 2.5 寄样管理（`/sample/deliveries`）

#### 页面与数据

| 项 | 内容 |
|---|---|
| 路由 | `/sample/deliveries` |
| 表 | `sample_deliveries` + 明细 + 费用（`sample/deliveries/models.py:15-89`） |

#### 状态机

| 当前 | 动作 | 结果 | 条件 |
|---|---|---|---|
| 草稿 | 提交审核 | 待审核 | — |
| 待审核 | 审核通过 | 已审核 | 审批人不能是提交人；通过后按明细写入样品「寄样」流水 |

| 待审核 | 撤回 | 草稿 | 提交人本人或超管；已有下游记账不能撤回 |
| 已审核 | 更新物流并寄出 | 已寄出 | 填快递公司/运单号/寄出时间；寄出后不能驳回或撤回 |
| 草稿 / 已退回 | 编辑 | 草稿 | 只有草稿、已退回能编辑；编辑会整体替换明细与费用 |

| 字段 | 说明 |
|---|---|
| 寄样日期、收件人、收件公司、收件地址 | 文本 |
| 客户标识 / 客户名称 | **手填文本**，不校验客户主数据 |
| 供应商 / 工厂 | 手填名称 |
| 快递公司 / 运单号 | 文本 |
| 报价单号 / 报价标识 | **手填文本**，不校验报价是否存在 |
| 明细 | 样品标识、样品编号、样品分类、产品编号/名称、数量、单位、备注；样品标识用来扣减留样 |
| 费用 | 快递费、保险费、其他；承担方公司/客户/供应商 |

#### 两点要注意

- 审核通过时才校验留样量；样品标识不存在时同样报「样品留样数量不足」，错误信息容易误导（`sample/deliveries/services.py:633-642`）。

### 2.6 出口合同（`/sales/contracts`，菜单「订单中心」）

#### 页面与数据

| 项 | 内容 |
|---|---|
| 路由 | `/sales/contracts`（`frontend/src/app/pages/sales/ExportContractsPage.tsx:28-64`） |
| 主表 / 行表 | `export_contracts` / `export_contract_lines`（`sales/contracts/models.py:15-108`） |
| 权限 | 查看 `sales:contract:view`、编辑 `sales:contract:edit`、审批 `sales:contract:approve`、导出 `sales:contract:export` |
| 指标 | 合同数、待审批、已审批、合同总额、预收款 |
| 列表列 | 合同号、状态、客户、计划出运日、金额、回签状态、详情 |
| 筛选 | 关键字（合同号/客户/贸易条款/来源报价/产品条码/规格/型号）、状态、客户（服务端搜索） |

列表默认**不显示已作废合同**；只有状态筛选选「已作废」才出现（`sales/contracts/repositories.py:420-423`）。

#### 状态机

| 当前 | 动作 | 结果 | 条件 |
|---|---|---|---|
| 草稿 | 提交审批 | 待审批 | 指定审批人，审批人需有 `sales:contract:approve` 且不能是提交人（`sales/contracts/services.py:229-262`） |
| 待审批 | 审批通过 | 已审批 | 只有被指定审批人/管理员能操作（`sales/contracts/services.py:263-311`） |
| 草稿 / 已审批 / 已退回 | 作废 | 已作废 | 必须填原因；不能有出货单、采购合同、收款分配、预收款（`sales/contracts/cancellation.py:41-61`） |
| 已作废 | 重开 | 新草稿合同 | 必须填原因；同一合同只能重开一次；复制全部行，已采购/已出货数量清零（`sales/contracts/cancellation.py:86-165`） |

两个关键缺口：

- **待审批没有「驳回」和「撤回」接口**，只能先审批通过再作废（或直接改库）。
- **数据里存在「已退回」状态，但没有入口能产生它**（`VALID_EXPORT_CONTRACT_STATUSES` 包含 rejected，路由里没有 reject/withdraw）。

#### 新建/编辑表单

| 字段 | 说明 |
|---|---|
| 合同号 | 自动生成 |
| 合同日期 | 日期 |
| 销售员 | 员工下拉（服务端加载可指派用户）；保存真实 `sales_user_id` |
| 客户 | 服务端搜索、只返回启用客户；选中后带出客户名称/币种/贸易条款 |
| 客户名称 | 只读快照 |
| 币种 / 贸易条款 / 付款条件 / 计划出运日 / 备注 | 文本或日期 |
| 明细 | 通过「添加商品」抽屉选择产品，可改条码、规格、型号、数量、单位、单价；金额实时计算；可删行、可清空 |

- 只有**草稿**能编辑，编辑会整体替换明细（`sales/contracts/services.py:112-157`）。
- 数量必须 > 0，单价必须 > 0；合同总额 = 行金额合计。
- 保存时统一校验：传了 `customer_id`、`sales_user_id` 或行 `product_id`，目标就必须存在且启用；编辑旧单时，与数据库原值相同的引用允许已停用（`sales/masterdata_refs.py`）。

#### 审批后还能做什么

- **回签登记**：任何状态都能登记，登记后回签状态变「已回签」；没有次数上限，也没有状态限制（`sales/contracts/services.py:340-364`）。
- **预收款登记**：任何状态都能登记，写 `付款方名称/金额/日期/币种/备注`；金额没有上限校验（`sales/contracts/services.py:366-389`）。
- **打印单据**：`GET /printing/export-contracts/{id}`，抬头/金额/明细用合同快照，**客户联系人实时读客户主数据**（`backend/app/modules/system/printing/services.py:206-220`）。
- **导出 PDF**：`GET /sales/contracts/{id}/export`，需要 `sales:contract:export`。

#### 下游单据

| 下游 | 入口 | 条件 |
|---|---|---|
| 出货明细 | 出货明细页从合同行生成 | 合同需已审批；每个合同只取**首个未出货行**，数量不能超过未出货量；同一合同不能重复选，跨合同币种必须一致；**出货明细审批通过后才回写**合同行已出货数量（`sales/shipments/services.py:69-124`、`234`） |
| 采购合同 | 采购合同页「从出口合同生成」 | 合同需已审批；取选中合同的**全部行**，按产品配件汇总数量；产品没有配件明细会直接拒绝；供应商必须存在且启用；采购合同审批通过后才回写合同行已采购数量，重复生成不会被拦截（`purchase/contracts/services.py:168-226`、`614-631`） |
| 收款 | 收款管理手工登记后分配到合同 | 作废前必须没有收款分配（`cancellation.py:56-57`） |
| QC / 跟单 / 仓库 | 以合同或合同行为来源 | 见后续章节 |

#### 快照口径

- 快照：合同号、客户名称、销售员名称、币种、贸易条款、付款条件、合同行产品编号/名称/条码/规格/型号/单价。
- 实时：打印时的客户主联系人；列表里的「已采购/已出货」进度（由下游审批回写合同行字段）；预收款合计。

### 2.7 一条完整走单顺序（照着做）

1. **建报价**：出口报价 → 选启用客户 → 填一行产品、数量、单价、运费 → 保存。
2. **审批报价**：详情 → 提交审批（指定审批人）→ 审批人审批通过。
3. **转合同**：详情 → 生成出口合同 → 填确认日期 → 得到草稿合同。
4. **补合同**：订单中心 → 载入编辑 → 补付款条件、计划出运日、条码/规格/型号 → 保存。
5. **审批合同**：提交审批 → 审批通过。
6. **并行分支**：
   - 采购：采购合同页从出口合同生成 → 审批 → 回写合同行已采购数量。
   - 样品：打样管理新建打样单 → 更新进度到「已完成/客户确认」→ 载入样品登记 → 寄样管理新建寄样单 → 提交审核 → 审核通过 → 更新物流寄出。
7. **出货与收款**：出货明细页从合同行生成 → 出运；收款管理登记收款并分配到合同。
8. **回签与归档**：合同详情登记客户回签；需要时打印单据/导出 PDF。

### 2.8 本章结论

- **报价是价格谈判层，合同是履约层。** 报价审批通过后才允许转合同；转合同只复制主干字段，运费、采购参考价不会带入，条码/规格/型号需要在合同里补齐。
- **样品是独立闭环。** 打样 → 样品登记 → 寄样这条链在样品模块内部是通的，但与报价只有「客户 + 产品」的弱反查。
- **合同是订单中心，也是所有下游的锚点。** 采购、出货、收款、QC、仓库都从合同或其行出发；合同一旦有下游单据就不能作废，只能重开。
- 本批已解决「新建引用不存在/停用主数据」和「下拉截断」两个基础问题；仍未解决的是：**报价 ↔ 样品没有结构化关联、待审批合同无驳回/撤回、签署与预收款无状态/金额约束、生成型动作无幂等键**（后两项进入第二批）。
