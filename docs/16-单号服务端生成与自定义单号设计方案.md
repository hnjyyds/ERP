# 单号服务端生成与自定义单号设计方案

- 设计时间：2026-11-07
- 状态：待确认，未改业务代码
- 范围：`frontend/src` 前端造号 38 处、`backend/app/modules` 相关唯一单号字段
- 目标：默认服务端生成、前端只读；可选自定义单号（默认关闭）；规则可配置；并发不重号

## 一、结论先行

1. 前端目前有 **38 处**用 `Date.now().toString().slice(-6)` 造号，覆盖 **16 个文件**。这些号既不是稳定序号，也不保证唯一，且部分被当作「外部编号」填了假值。
2. 后端所有单号字段都已有 `unique=True, nullable=False`，说明**唯一性底座已经存在**，缺的是「服务端生成 + 规则配置 + 冲突错误定位」。
3. 编号分三类，不能一把梭：
   - **A 类 ERP 内部单号**：应当服务端生成（如入库单、出库单、采购合同）。
   - **B 类 外部来源编号**：不应生成，必须人工录入（如报关单号、供应商发票号）。当前前端给它们造了假值，属于数据污染。
   - **C 类 引用/子记录编号**：跟随来源单据，不应独立生成（如报价转合同的合同号、合同收付款计划号）。
4. 方案落三张表：`system_number_rules`（规则）、`system_number_sequences`（计数）、`system_number_audits`（自定义单号审计）。生成走数据库原子自增，唯一索引兜底。
5. 先试点入库单 + 出库单，验证并发生成、自定义冲突、前端只读三项，再按模块铺开。

### 2.3 编号分类结论

| 类别 | 处理方式 | 涉及 |
| --- | --- | --- |
| A 内部单号 | 服务端生成，可自定义 | 入库/出库/采购询价/采购合同/报价/出口合同/出运计划/样品登记/寄样申请/寄样单/QC/财务内部单号/基础资料编码 |
| B 外部编号 | **删除假默认值**，改为必填人工录入 | `SI-`、`PFI-`、`CD-`、`CR-`（含采购开票通知的 `CD-`） |
| C 引用/子记录 | 跟随来源单，不独立生成 | 报价转合同的 `contract_no`、合同收付款计划 `AR-`、`customs-` 临时 ID |

**关键判断**：B 类现在被前端伪造，会让财务/报关数据看起来「有编号」，实际是假的。这部分不需要等编号服务，可在试点前先单独清理。

## 三、目标形态

### 3.1 默认生成、前端只读

- 新建表单中单号字段默认**禁用**，显示占位文案「保存后自动生成」，不预先填充任何值。
- 提交时前端不传 `code`（或传 `custom_number=false`），由后端生成并在响应里返回。
- 前端列表/详情/打印统一使用后端返回的 `code`。

### 3.2 自定义单号开关

- 表单内提供「自定义单号」开关，默认关闭；仅当用户拥有权限时可见。
- 开启后单号输入框才可编辑，且**不自动填充**任何默认值，由用户完整输入。
- 关闭开关时清空已输入内容，回到系统生成。
- 编辑已有单据时单号只读（建议单号创建后不可修改，见待确认项）。

### 3.3 错误与字段定位

复用现有错误响应结构，不新增顶层 `code` 语义：

```json
{
  "success": false,
  "code": "CONFLICT",
  "message": "单号已存在",
  "error": {
    "code": "CONFLICT",
    "message": "单号已存在",
    "details": [
      { "field": "code", "message": "单号已存在，请更换", "type": "unique" }
    ]
  }
}
```

- 字段名固定为单据的编号字段名（`code` / `receipt_no` / `settlement_no` 等）。
- 前端按 `details[].field` 把提示挂到对应输入框，而不是只弹 toast。
- 语言由 `Accept-Language` 决定，错误码稳定可枚举。

## 六、生成算法与并发

### 6.1 生成流程

1. 按 `doc_type` 读规则（进程内缓存 + 版本号，修改后失效）。
2. 用服务器时区（当前为 `Asia/Shanghai`）计算 `period_key`。
3. 同一事务内原子自增序号：

```sql
INSERT INTO system_number_sequences (doc_type, period_key, current_value)
VALUES (:doc_type, :period_key, 1)
ON CONFLICT (doc_type, period_key)
DO UPDATE SET current_value = system_number_sequences.current_value + 1,
              updated_at = now()
RETURNING current_value;
```

4. 按 `prefix + separator + date + separator + 左补零序号` 拼出单号。
5. 先占用序号、再插入业务行；业务行插入失败则整个事务回滚，**允许跳号，不允许重号**。
6. 业务表 `unique` 约束是最后一道防线；若仍冲突，重新取号重试（最多 3 次），超过则报系统错误。

### 6.2 并发与多实例

- 自增在数据库单条语句内完成，天然支持多进程/多实例，不需要 Redis 或应用锁。
- 所有写路径先写 `system_number_sequences` 再写业务表，固定锁顺序，避免死锁。
- 测试库若为 SQLite，用「事务内 `UPDATE ... WHERE` 影响行数为 0 则 `INSERT`，冲突重试」实现相同语义。
- 号段缓存（每次取 100 个）在重启时会丢号，**首版不做**，优先保证连续可解释。

### 6.3 自定义单号流程

1. 校验权限 → 校验长度/字符/正则 → 去除首尾空格。
2. 先查重（快速失败），再插入业务行；`IntegrityError` 统一翻译成字段级冲突错误。
3. 写入 `system_number_audits`（`mode=custom`，成功与被拒都记）。
4. 自定义单号**不占用**自动序号，避免出现「用了自定义号后自动号跳一大段」以外的关联问题。

## 七、自定义单号：权限与审计

- 新增权限 `numbering.custom.<domain>`，默认只授予管理员；普通用户看不到开关。
- 关闭开关是默认路径，前端不传 `custom_number` 时一律走生成。
- 审计字段：操作人、`request_id`、单据类型、单号、结果、时间。
- 冲突响应必须带 `details[].field`，前端定位到输入框。
- 建议限制：单号创建后不可修改；如必须改，要求「作废重开」而不是原地改号。

## 八、接口契约

### 8.1 创建接口

- 请求新增可选字段：`custom_number: bool = false`、`code: str | None`。
- `custom_number=false`：忽略传入的 `code`，服务端生成。
- `custom_number=true`：`code` 必填，走自定义校验。
- 响应继续返回既有 `code` 字段，结构不变。

这样旧前端（只传 `code`、不传 `custom_number`）仍然可用，只是拿到的号变成服务端生成的，属于向后兼容的期望变化。

### 8.2 规则管理接口

## 九、迁移与历史数据兼容

1. 新增 Alembic 迁移：建 3 张表 + 按第五节写入默认规则；**不改动任何业务表结构**。
2. 历史单号原样保留，不做格式回填；`unique` 约束不变。
3. 新规则默认格式与历史不冲突（历史是 `IO-######`，新格式含日期段，天然区分）。
4. 若管理员把规则改成与历史同格式，唯一索引会拦截冲突并触发重新取号。
5. 旧前端灰度期间：服务端忽略其传入的 `code` 并用生成号返回，列表刷新后展示新号。
6. 回滚：功能开关 `numbering.enabled=false` 时仍接受客户端单号（回到旧行为），表可保留。

## 十二、验收标准

- 并发生成：50 个并发请求创建同类单据，得到 50 个不同单号，无 500。
- 重置周期：跨日/跨月/跨年后序号从 1 开始，`period_key` 正确。
- 自定义冲突：重复单号返回 `CONFLICT`，`details[0].field` 等于该单据编号字段，前端提示挂在输入框。
- 语言：`Accept-Language: en-US` 时冲突文案为英文，错误码不变。
- 兼容：不传 `custom_number` 的旧请求仍成功，响应结构不变。
- 历史数据：迁移前后单号、唯一索引、列表展示无变化。
