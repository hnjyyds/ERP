# 单号随机生成方案（内部单号）与外部编号手填规则

- 修订时间：2026-11-07
- 状态：已按新口径修订，试点范围为入库单 + 出库单
- 取代：本文上一版「服务端序号生成 + 可选自定义单号」
- 范围：`frontend/src` 前端造号位置、`backend/app/modules` 相关唯一编号字段

## 一、结论先行

1. **内部单据号随机自动生成**，格式为 `单据类型前缀-随机段`，例如 `XP-IN-7K3M9Q`。前端只读，不提供选择、改写或默认值。
2. **唯一性靠数据库唯一约束 + 冲突重试**，不先查后插。允许「跳号」这一概念不存在（随机号没有序号），绝不允许重号。
3. **外部编号不生成、无默认值，改为必填手填**（供应商发票号、报关单号、收据号等）。缺失时前端阻断提交，并把错误挂在该字段上。
4. **单号创建后不可修改**：当前后端没有通用更新接口，后续新增更新接口时必须拒绝写入编号字段；前端任何编辑态都只读。业务更正走「作废重开」，新单保留与旧单的关联关系。
5. **取消「自定义单号开关」及配套权限设计**。内部号完全自动、外部号纯手填，不再提供覆盖入口。
6. **审计表不再保留**：没有自定义号就没有「谁改过号」需要审计；作废重开尚未实现，待该功能落地时用业务表字段记录关联（见第七节），避免现在建一张空转的表。
7. **基础资料编码暂不改**，两种方案影响对比见第八节，等确认后再动。
8. 实施顺序：先改本文，再只落地入库单 + 出库单（后端生成 + 前端只读 + 历史数据兼容），验证通过后汇报，再铺开其余单据类型。

### 2.3 编号分类结论

| 类别 | 处理方式 | 涉及 |

| A 内部单号 | 服务端随机生成，前端只读 | 入库/出库/采购询价/采购合同/报价/出口合同/出运计划/样品登记/寄样申请/寄样单/QC/财务内部单号/基础资料编码 |

## 三、内部单号：格式与生成

### 3.1 格式

```
{前缀}-{随机段}
XP-IN-7K3M9Q
XP-OUT-4H8N2R
```

- 前缀按单据类型固定，集中在后端注册表里声明，不允许页面各自拼字符串。
- 随机段长度统一为 **6**，字符集为 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`（31 个字符）。
- 排除易混淆字符：`0`、`O`、`1`、`I`、`l`；字母统一大写。
- 分隔符固定 `-`，前缀本身可含 `-`（如 `XP-IN`）。

试点前缀：

| doc_type | 前缀 | 目标字段 |
| --- | --- | --- |
| `warehouse.inbound_order` | `XP-IN` | `warehouse_inbound_orders.code` |
| `warehouse.outbound_order` | `XP-OUT` | `warehouse_outbound_orders.code` |

其余单据类型的默认前缀沿用现有业务前缀（`PI`、`PC`、`QT`、`EC`、`SP`、`SR`、`SM`、`SD`、`QC`、`BR`、`PR`、`FS` 等），铺开时在注册表逐项确认。

### 3.2 碰撞概率估算

随机段 6 位、字符集 31 个字符：

- 空间 `N = 31^6 = 887,503,681`（约 8.9 亿）。
- 单次插入与「已有 n 条同类单号」碰撞的概率 `p ≈ n / N`。
  - n = 10,000：`p ≈ 1.1 × 10^-5`
  - n = 100,000：`p ≈ 1.1 × 10^-4`
  - n = 1,000,000：`p ≈ 1.1 × 10^-3`
- 生日问题下「n 条记录中至少出现一次碰撞」的概率 `1 - exp(-n² / 2N)`：
  - n = 1,000：约 0.06%
  - n = 10,000：约 5.6%
  - n = 100,000：接近 99.6%

生日概率描述的是「历史上出现过多少次碰撞」，而不是「一次插入会不会失败」。因为碰撞由唯一约束拦截并自动重试，真正的失败概率是 `p^k`：

- 重试上限 `k = 3`：
  - n = 10,000：`(1.1e-5)^3 ≈ 1.3e-15`
  - n = 1,000,000：`(1.1e-3)^3 ≈ 1.3e-9`

结论：6 位在单类型百万级数据量下仍有足够余量；若未来单类型超过约 500 万条，建议把随机段扩到 7 位（`31^7 ≈ 275 亿`），只需改注册表常量并保持历史号不变。

### 3.3 生成流程（并发安全）

```
for attempt in 1..3:
    code = 前缀 + "-" + 随机段
    try:
        事务内插入业务行（唯一约束兜底）
        commit
        return
    except IntegrityError as exc:
        if 不是 code 唯一冲突: raise
        rollback（UnitOfWork 自动完成）
        继续下一次
raise DocumentNumberConflictError
```

要点：

- **不先查后插**。查询与插入之间存在竞态，查重不能作为唯一性依据；唯一约束才是唯一性来源。
- 每次重试重新生成随机段，不复用失败的号。
- 冲突只重试「编号列唯一冲突」，其他完整性错误直接抛出，避免把真实数据问题掩盖成单号问题。
- 重试在事务外循环：`IntegrityError` 会让当前事务失效，必须整体回滚后重开事务，而不是在同一事务里继续。
- 多实例/多进程天然安全：唯一约束在数据库端，不依赖应用锁、Redis 或号段缓存。
- 允许跳号/空洞：随机号本身不承诺连续，失败的插入不会留下业务行。
- 重试上限 3 次，超过后返回稳定错误码 `CONFLICT`，文案「单号生成失败，请重试」，并记录 `request_id` 便于排查。

### 3.4 不可修改

- 单号只在创建时写入一次。
- 现有入库单/出库单没有通用更新接口，只有 `submit` / `approve` 状态流转，均不写 `code`。
- 后续新增更新接口时，schema 中不得包含编号字段；如客户端传入，服务端忽略或直接拒绝。
- 前端编辑态（含复制、转单等入口）单号输入框一律只读，不提供覆盖入口。
- 业务上确需更正，走「作废重开」：原单作废，新单重新生成新号，并通过关联字段指向原单。

## 四、外部编号：必填手填

- 外部编号（供应商发票号、报关单号、报关收据号、合作方费用发票号等）**不生成、不设默认值、不做兜底占位**。
- 表单中为普通文本输入，`required`，初始值为空。
- 提交时若为空：前端阻断提交，把错误提示挂在该字段下方（字段级错误），不只弹全局 toast。
- 后端继续保留非空约束与长度校验，作为第二道防线；校验错误通过 `details[].field` 返回，字段名与前端表单字段一致。
- 历史数据中由前端伪造的外部编号原样保留，不自动清洗；后续如需清理，按单据类型单独盘点并在迁移脚本中处理。

试点（入库单/出库单）不包含外部编号字段，本规则从第九节批次 5 开始落地。

## 五、接口契约

### 5.1 创建接口

- `code` 从必填改为**可选**，仅用于兼容旧前端；服务端**忽略**传入值，始终生成新号。
- 新增字段仅 `code?: string | null`，不引入 `custom_number` 开关。
- 响应结构不变，继续返回生成的 `code`。

这样旧前端仍可调用，但拿到的号是服务端生成的；前端升级后不再传 `code`。

### 5.2 不再提供的接口

- 删除规则管理接口（`/system/numbering/rules`）。
- 删除单号预览接口（随机号无法预览「下一个号」）。
- 删除自定义单号相关权限键。

## 六、数据模型

**试点不新增任何表，也不改业务表结构。**

- 前缀、随机段长度、字符集以代码常量/注册表维护。规则极简（只有前缀和随机长度），没有日期段、序号、重置周期，配置表会退化为「三个字段的表」，收益不足；等铺开后若确需按环境调整前缀，再引入轻量配置。
- 唯一性由业务表现有 `unique` 约束保证。
- 不需要序号表：随机号没有「当前值」。
- 不需要自定义号审计表：不存在自定义号；作废重开的关联记录见第七节。

## 七、作废重开与审计（设计，未实施）

- 作废：`status = cancelled`（入库单/出库单状态枚举已含 `cancelled`），保留原单与单号。
- 重开：新建单据，生成新号，并在业务表增加 `reissued_from_id`（可空，指向原单）与 `reissue_reason`。
- 关联关系可通过列表/详情展示「由 XXX 作废重开」。
- 待作废重开功能落地时，再评估是否需要独立审计表记录操作人、时间、原因；当前不建表，避免空转。

## 八、基础资料编码：两种方案影响对比（暂不改，等确认）

| 维度 | 方案 A：同样随机生成 | 方案 B：保持手填/外部编码 |
| --- | --- | --- |
| 唯一性 | 与单据一致，唯一约束 + 重试 | 依赖人工，重码时由唯一约束报错 |
| 录入效率 | 高，用户不关心编码 | 低，客户/供应商/商品编码常来自外部系统 |
| 与外部系统对接 | 需要额外维护「外部编码 ↔ 内部编码」映射 | 直接使用外部编码，天然对齐 |
| 导入流程 | 导入文件里的编码会被忽略或需要改写 | 导入文件编码可直接落库 |
| 可读性 | `XP-PRD-7K3M9Q` 无法表达品类/规格 | 业务编码通常自带含义（如 `BAG-40`） |
| 历史数据 | 与现有 `P-`/`CUS-` 等格式并存，需要确认无冲突 | 无变化 |
| 改动范围 | 商品/客户/供应商/合作方/单证主体 5 类页面 + 导入 | 仅删除前端 `Date.now()` 默认值，改为必填 |
| 风险 | 外部对接方可能要求固定编码 | 无新增风险 |

倾向建议：**方案 B**。基础资料编码通常由外部体系或业务规则决定，随机化会破坏对接与可读性；但最终由用户确认。

## 十一、迁移与历史数据兼容

1. **无 Alembic 迁移**：不新增表、不改字段、不改索引。
2. 历史单号原样保留，不做格式回填、不重排。
3. 新格式 `XP-IN-XXXXXX` / `XP-OUT-XXXXXX` 与历史 `IO-######` / `OO-######` 不冲突；即使前缀被改成与历史相同，唯一约束仍会拦截并触发重试。
4. 旧前端灰度期间：服务端忽略其传入的 `code`，返回生成号；前端刷新后展示新号。
5. 回滚：代码回退即可恢复「接受客户端 `code`」的旧行为；已生成的数据不受影响。

## 十二、验收标准

- 生成格式：入库单 `XP-IN-[A-Z2-9]{6}`，出库单 `XP-OUT-[A-Z2-9]{6}`，不含 `O/0/I/1/l`。
- 忽略客户端号：请求传 `code=IO-API-001`，返回的 `code` 不等于该值。
- 并发唯一：并发创建同类单据，全部成功且单号互不相同。
- 冲突重试：模拟插入时先遇到一次唯一冲突，第二次成功，最终只落一条记录。
- 重试耗尽：连续 3 次冲突返回 `CONFLICT`，无残留业务行。
- 历史数据：迁移前后历史单号与列表展示无变化。
- 前端：新建弹窗单号输入框只读、无默认值；提交成功后列表/提示展示后端生成的号。
