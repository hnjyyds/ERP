### AUD-001 商品编码允许纯空白（P2）

状态：已完成

- 根因：`backend/app/modules/masterdata/products/schemas.py:14` 等字段仅用 `min_length=1`，不排除空白；`products/services.py` 创建时直接使用原值。
- 方案：
  1. 在 `schemas.py` 为 `ProductCreate`、`ProductUpdate`、`ProductAccessoryCreate` 的必填文本字段增加统一的 `field_validator`：`value.strip()` 后为空则报错，返回去空白值。
  2. 将同一规范化函数放到 `backend/app/core/validators.py`（新建），供其他模块复用，不逐模块复制。
  3. 唯一性检查改为针对规范化后的 `code`；`repositories.py` 的 `find_by_code` 入参先 `strip()`。
- 测试：`backend/tests/api/test_products.py` 新增「纯空白 code 返回 422」「` code ` 落库为 `code`」「带空格与无空格重复编码冲突」。
- 验收：API 不再出现 `length(code)=3 && trim(code)=''` 的记录；空白名称、单位同样被拒绝。
- 风险：历史记录中已存在纯空白编码，需在批 3 数据核验时列出，不自动删除。

### AUD-004 收款并发分摊突破余额（P1）

状态：已完成

- 根因：`finance/receipts/services.py:138-165` 先读 `receipt.unallocated_amount`（`:146-147`）再进入 `UnitOfWork` 写分摊；`repositories.py:431-454` 只是在读取时做 `max(amount - allocated_amount, 0)`，没有写入侧约束。
- 方案：
  1. 在 `receipts/repositories.py` 新增 `try_reserve_allocation(receipt_id, amount)`：执行
     `UPDATE bank_receipts SET allocated_amount = allocated_amount + :amount WHERE id = :id AND status <> 'unclaimed' AND allocated_amount + :amount <= amount`，返回 `rowcount`。
  2. `allocate_receipt` 在 `UnitOfWork` 内先 `try_reserve_allocation`，`rowcount == 0` 时抛出明确的业务冲突错误（映射为 409），再插入 `ReceiptAllocation`；`refresh_receipt_status` 只负责状态与冗余值回填，不再作为校验点。
  3. 保留 `_validate_allocation` 作为快速失败提示，但不再作为并发正确性的依据。
  4. 为 SQLite 增加写入串行化保障：连接参数设置 `busy_timeout`（`backend/app/core/database.py` 已有连接配置处），避免两个事务同时写时直接返回 `database is locked`。
  5. `unallocated_amount` 的 `max(..., 0)` 保留用于展示，但聚合超出时写审计日志，便于发现历史脏数据。
- 测试：`backend/tests/api/test_receipts.py` 新增「同一水单两笔并发分摊只成功一笔」「累计恰好等于余额时成功」「超额请求返回 409 且无分摊记录」「重试不产生重复分摊」。
  并发通过两个独立 `Session`/连接同时提交模拟，不使用线程池打真实 HTTP。
- 验收：数据库聚合满足 `SUM(allocation.amount) <= receipt.amount`；页面“未分摊”不再出现负数与 0 互相矛盾。
- 风险：`allocated_amount` 的维护路径必须唯一；若其他流程也写该列，需要先收敛到同一方法。

### AUD-005 付款并发审批突破发票余额（P1）

状态：已完成

- 根因：`finance/payments/services.py:187-234` 审批前读取并校验发票余额（`:204-205`），审批与分摊写入在 `UnitOfWork` 内但无原子余额条件；`payments/repositories.py:101-139` 初始化 `paid_amount=0`，后续按分摊回填。
- 方案：
  1. `payments/repositories.py` 新增 `try_reserve_payment(invoice_id, amount)`：条件更新
     `UPDATE supplier_invoices SET paid_amount = paid_amount + :amount WHERE id = :id AND paid_amount + :amount <= total_amount`，返回 `rowcount`。
  2. `approve_payment_request` 在同一 `UnitOfWork` 内依次执行：条件更新审批状态（仅 `pending`）→ `try_reserve_payment` → `add_allocation`；任一步 `rowcount == 0` 抛 409。
  3. 审批状态更新必须带 `WHERE status = 'pending'`，防止重复审批并发进入。
  4. `refresh_supplier_invoice_status` 不再允许把 `paid_amount > total_amount` 归一成“已付清且未付 0”；超限时保持原值并触发审计。
- 测试：`backend/tests/api/test_payments.py` 新增「两张付款申请并发审批只成功一张」「重复审批同一申请第二次 409」「已付清发票再次审批被拒」「分摊合计等于发票金额时状态为已付清」。
- 验收：`paid_amount <= total_amount`；不存在“已付清但分摊合计超额”的记录。
- 风险：审批流涉及审计与通知，条件更新失败时不得写审计；需保证事务回滚覆盖通知副作用（通知在提交后发送）。

### AUD-009 CSV 文本保留公式前缀（P2）

状态：已完成

- 根因：`backend/app/modules/masterdata/products/services.py:284-312` 使用 `csv.writer` 直接写用户文本；引号转义不能阻止电子表格把 `=`、`+`、`-`、`@`、`\t`、`\r` 开头的内容当公式解析。
- 方案：
  1. 新建 `backend/app/core/csv_export.py`，提供 `safe_cell(value, *, numeric=False)`：文本单元格以 `= + - @ \t \r` 开头时前置 `'`；数值列不处理。
  2. 商品导出改用该函数，并把 `tax_rate`、`rebate_rate` 作为数值列输出。
  3. 盘点其他直接写 CSV 的导出（报价、合同、样品、报表），按同一函数逐个替换；替换清单在实现时补入本文“改动文件”表。
- 测试：`backend/tests/services/test_csv_export.py` 覆盖 `=1+1`、`+1`、`-1`、`@cmd`、制表符、换行、含引号与逗号；`test_products_export_formula_injection` 断言导出内容以 `'=` 开头。
- 验收：文本样例在导出 CSV 中始终保持普通文本；金额/税率仍可被表格识别为数值。
- 风险：`-1` 这类合法负数文本会被加前缀；因此只对“文本列”启用，数值列显式排除。

### AUD-010 “导出全部”被分页截断（P2）

状态：已完成

- 根因：`api/pagination.py:57-101` 对所有 GET 注入默认 `limit=50`；`core/pagination.py:29-31` 的 `resolve_limit` 优先读取该上下文；`products/services.py:290` 的 `limit=10_000` 实际被改成 50，超出 10,000 也静默截断。
- 方案：
  1. `PaginationMiddleware` 增加导出路径豁免：路径以 `/export` 结尾时不启动分页上下文（仍校验 `limit/offset` 合法性），使 `resolve_limit` 回落到调用方传入值。
  2. `products/services.py:290` 改为显式批读取 `list_products(limit=None, offset=0)`，并让 `repositories.list_products` 在 `limit is None` 时省略 `.limit()`；不设隐式上限。
  3. 若性能评审要求保留上限，则在响应中返回 `X-Export-Truncated: true` 与 `X-Export-Total`，前端导出后提示“已导出前 N 条”，不再把截断结果称为全部。
  4. 增加回归用例覆盖 `/export` 路由不进入分页上下文。
- 测试：`backend/tests/api/test_products.py`「51 条数据导出 51 行」「带 `?limit=5` 的导出仍返回全量」「`offset` 不影响导出」。
- 验收：导出条数与总数一致；如启用上限，响应头明确告知。
- 风险：全量导出内存占用；产品量级可接受，后续可改流式 `StreamingResponse`。
