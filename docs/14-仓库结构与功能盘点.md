## 0. 结论摘要

### 0.1 五条总判断

1. **后端结构是这个仓库最健康的部分。** 10 个业务域、38 个子模块，统一采用“路由 → 服务 → 仓储 → 模型”的模块化单体分层；跨模块编排集中在 `providers.py`；写操作统一用 `UnitOfWork` 控制事务；架构测试强制了 API 层不碰模型/仓储、仓储不提交事务、路由必须有响应模型、单文件不超过 700 行。这些不是口头约定，而是有测试兜底的。
2. **前端能支撑现有业务，但已经进入“继续加功能会变慢”的状态。** 页面按业务域拆分本身合理，问题集中在四个超大文件：`FinancePage.tsx` 6,826 行、`api.ts` 6,055 行、`styles.css` 9,532 行，以及完全未被引用的 Vue 遗留文件 `App.vue` 13,681 行。
3. **部署是“能跑的单机方案”，不是文档里写的生产架构。** 实际是单副本 FastAPI + SQLite 文件 + 本地文件目录 + Nginx；没有 PostgreSQL、Redis、MinIO、Celery、Alembic。`docs/03` 描述的是目标架构，但没有标注“目标”，容易被误读为现状。
4. **文档数量多、分阶段验收记录细，但一致性差。** 34 份 `docs/checks` 中，多份仍停留在阶段验收时点（例如说商品导入未实现、客户交易记录返回空列表、通知已读未实现），而代码已经补上；`docs/03`、`docs/04`、根目录 `FRONTEND_IMPLEMENTATION_STATUS.md` 则明显落后于代码。
5. **功能主干已经跑通，缺口集中在三类：** 采购/开票的页面前端仍是演示表单；单据状态机只有“通过”没有“驳回/作废/撤回”；仓储缺少仓库/库位主数据、库存调拨和独立库存页面。单证管理整体尚未实现。

### 0.2 结构判断

| 维度 | 判断 | 主要依据 |
| --- | --- | --- |
| 后端分层 | 良好 | 38 个子模块结构一致；事务、依赖注入、架构测试完整；无导入环 |
| 前端分层 | 可用，需治理 | 页面按域拆分合理；`FinancePage`、`api.ts`、`styles.css` 过大；全局 CSS 无作用域 |
| 数据边界 | 有一处明显倒置 | 库存模型属于入库单模块，却被商品和出库模块反向依赖 |
| 状态流转 | 不完整 | 多数枚举定义了 `rejected/cancelled`，但没有可达接口 |

### 0.3 最优先处理的七件事

1. 清理采购合同生成、采购询价、开票通知页面里的演示默认值和“手填 UUID”交互（直接影响业务可用性）。

5. 重写或明确标注 `docs/03`、`docs/04` 为“目标架构/目标模型”，并更新 `FRONTEND_IMPLEMENTATION_STATUS.md`。

## 2. 结构问题清单

判断口径：
- **P0**：投产或正式交付前必须处理，否则有数据/升级风险。
- **P1**：影响核心业务可用性或后续开发效率，建议近期处理。
- **P2**：一致性、整洁度问题，可随手修，不影响当前功能。

### P0-1 数据库结构变更没有版本化迁移

- **状态**：已解决（`ae05741`）。引入 Alembic（`backend/migrations/`），生成基线并删除全部 `ensure_*` 启动补丁，后续结构变更走版本化迁移。

**现象**
- 启动时先 `Base.metadata.create_all`，再逐个调用 11 个 `ensure_*` 函数执行手写 `ALTER TABLE`：`backend/app/main.py`（启动流程）以及 `system/auth`、`system/company`、`system/dashboard`、`system/mcp_settings`、`system/approval_assignments`、`masterdata/products`、`sales/contracts`、`purchase/contracts`、`quality/inspections`、`warehouse/inbound_orders`、`finance/port_data` 的 `migrations.py`。
- 文档 `docs/03-架构设计.md:354-358` 明确写的是 PostgreSQL + Alembic，并要求“所有表结构变更必须生成迁移脚本”。

**影响**
- 没有版本号、没有升级/回滚记录，无法回答“某个环境当前是什么结构”。
- 只支持新增列这类能被 `ALTER TABLE` 覆盖的变更；改类型、删列、加约束、索引变更没有统一路径。
- 如果模型改了列但忘记补 `ensure_*`，已存在的 SQLite 文件会静默缺列，只有运行到相关查询时才报错。
- 多副本部署时，多个进程同时执行 DDL 存在竞态（现在单副本，所以还没暴露）。

**是否值得改**：值得，投产前必须。当前单机开发环境可以暂时接受。

**代价与做法**：中等。建议先引入 Alembic 并生成一次基线，保留 SQLite 作为当前数据库；把 11 个 `ensure_*` 转成第一版迁移；在 CI 中增加“模型变更必须带迁移”的检查。不建议现在直接切 PostgreSQL——迁移版本化比换数据库更紧迫。

### P1-1 库存模型归属错误，导致跨模块反向依赖

- **状态**：已解决（`d3257e7`）。库存余额/流水模型迁入 `warehouse/inventory/`，商品与出入库模块改为依赖独立库存模块。

**现象**
- `InventoryBalance`、`InventoryLedger` 定义在 `backend/app/modules/warehouse/inbound_orders/models.py`。
- 库存查询接口挂在入库单路由下：`backend/app/api/v1/inbound_orders.py:59` 和 `:78`（`/warehouse/inbound-orders/inventory-balances`、`/inventory-ledgers`）。
- 商品模块为了展示库存流水直接导入入库单模型：`backend/app/modules/masterdata/products/repositories.py`。
- 出库模块为了扣减库存直接导入入库单仓储/模型：`backend/app/modules/warehouse/outbound_orders/repositories.py`。

### 2.7 有意为之、不算问题的设计

- **模块化单体而不是微服务**：当前团队和业务规模下，单进程、单数据库更简单；模块边界通过目录和测试维持。
- **API 层薄、服务层编排、仓储层数据访问**：三层职责清晰，且由架构测试强制。
- **写操作统一 `UnitOfWork`**：38 个服务中 32 个使用；其余 6 个是财务总览、报表、打印、扫描等只读服务，不使用是合理的。
- **跨模块编排放在 providers**：采购合同同时依赖销售合同、主数据、跟单，这种显式装配比在服务里到处 import 更可控。
- **删除用停用/草稿删除，不做硬删除**：符合业务可追溯要求，是正确取舍。
- **单据生成链路集中在一个事务**：报价 → 合同 → 采购合同 → 入库计划/跟单计划；合同 → 出货 → 出库计划，链路明确。
- **只读模块没有 models**：`reporting/approvals`、`reporting/statistics`、`finance/overview`、`finance/reports` 只做读模型，合理。
- **每个模块自带事件表**（`sales_contract_events`、`quality_inspection_events` 等）而不是统一 outbox：当前没有异步消息系统，这样足够。
- **后端 700 行文件上限**：由 `tests/architecture/test_backend_file_boundaries.py` 强制，是有意的质量约束。
- **前端按域拆页面、主数据页共用 `TradingPartnerPage`**：不是重复代码，是有意的模板化 CRUD。
- **SQLite + 本地文件**：单机、小数据量、内网部署下可用；问题不在 SQLite 本身，而在于文档把它写成了 PostgreSQL/对象存储架构。
- **采购询价/开票通知归入“暂缓模块”**：是产品优先级决策，不是技术债；但页面里的演示数据和可创建入口仍应处理。

### 3.5 样品管理

**位置**：`modules/sample/{requests,records,deliveries}`；前端 `SampleRequestsPage.tsx`、`SampleRecordsPage.tsx`、`SampleDeliveriesPage.tsx`。

**已落地**

- 样品登记：创建、列表、导入、导出、图片、库存变动（入库/出库/调整）、详情。
- 寄样：创建、编辑、提交、审批、驳回、撤回、物流状态更新、费用统计、寄样/报价历史、导出。
- 寄样驳回：`submitted → rejected`，仅指定审批人可操作，原因必填（`rejected_at`、`rejection_reason`）；撤回：`submitted → draft`，提交人或管理员可操作，清空 `submitted_at`/`reviewer_id`/`reviewer_name`。编辑已驳回单自动回草稿并保留原因展示，直到重新提交才清空。驳回/撤回前显式校验未进入 `shipped`、且寄样明细中的样品未产生 `delivered` 库存事件（`4680f7e`、`bd29695`）。
- `rejected` 状态与 `draft`/`submitted` 一样禁止物流更新：前端仅在 `approved`/`shipped` 启用物流表单，后端也拒绝非 `approved`/`shipped` 起始状态；被驳回后需先编辑回草稿、重新提交并由审批通过，才能继续更新物流（`caa2f9e`、`4680f7e`）。
- 寄样物流更新只允许从 `approved`/`shipped` 发起，目标状态限 `approved`/`shipped`，`shipped` 不可回退；`draft`/`submitted`/`rejected` 会被拒绝，前端在未审批时禁用物流表单（`caa2f9e`）。
- 手工登记样品发货数量时，寄样单号命中系统寄样单或已有同号发货流水会被拒绝；寄样单审批写入前也会校验同号流水，避免手工登记与审批重复扣减库存。不填寄样单号的线下补录仍可用（`8aea041`）。
- 打样申请新建只允许草稿/已发送/进行中；进度不能取消或回退，`completed` 仅能在 `customer_confirmed` 阶段且申请已进入进行中时写入，前端同步收敛可选项（`b2541c1`）。

**缺口**
- 打样申请不能编辑、取消或关闭；`cancelled` 状态不可达。
- 样品登记不能修改/删除，只能追加图片和库存事件；这是可追溯性设计，但录错后没有更正路径。
- 寄样审批已支持驳回/撤回；已生成发货流水或进入 `shipped` 后不可驳回/撤回。

**缺口**
- 出口合同审批只有通过，`rejected` 不可达；出口报价已支持驳回/撤回，出口合同无作废、撤回。

- 没有独立的“采购计划”实体，采购合同承担了计划角色（这是当前取舍，但与 `docs/02` 的模型清单不一致）。
- 出货审批后会自动回写合同已出货数量和跟单节点，但出库计划需要单独生成（设计如此）。

### 3.14 跨域主流程

| 流程 | 代码中的实际链路 | 状态 |
| --- | --- | --- |
| 报价 → 合同 | 报价审批后 `confirm-contract` 生成出口合同草稿 | 跑通 |
| 合同 → 采购合同 | 采购合同消费已审批出口合同，支持多合同合并；但前端要手填合同 ID | 后端跑通，前端半成品 |
| 采购合同 → 入库计划 | 采购合同审批通过自动创建入库计划 | 跑通 |
| 采购合同 → 跟单计划 | 采购合同审批通过自动创建跟单计划 | 跑通 |
| 合同 → 出货 → 出库 | 出货从合同生成；出库计划从出货生成；出库审批回写跟单 | 跑通 |
| QC → 入库 | 入库单审批调用入库资格接口，未通过则拦截 | 跑通 |
| 出货 → 财务 | 出货提供应收来源；收款、结算、退税按出货关联 | 跑通 |
| 开票通知 → 催收 → 收票 | 发送后生成提醒，登记税票后关闭提醒 | 跑通（报关数据为手工录入） |
| 单证 → 开票/退税 | 无单证模块，靠手工录入代替 | 未闭环 |

## 4. 状态流转盘点

| 单据 | 已实现流转 | 缺口 |
| --- | --- | --- |
| 出口报价 | 草稿 → 已提交 → 已审批 → 已生成合同；已提交可驳回（→已驳回）或撤回（→草稿）；已驳回编辑自动回草稿，重新提交时清空驳回原因 | 无作废；已生成合同后不可驳回/撤回；驳回/撤回前显式校验下游合同（`edada1e`、`31eb170`） |
| 出口合同 | 草稿 → 已提交 → 已审批 → 已签字；可登记预付款 | 无驳回/作废/关闭 |
| 出货明细 | 从合同生成 → 已提交 → 已审批；已提交可驳回（→已驳回）或撤回（→草稿）；已驳回可通过「从合同重新同步」回到草稿并刷新合同当前明细 | 无自由编辑/作废；驳回/撤回/同步前均校验未生成出库计划；同步不接受自定义数量（`284c42e`、`f80f8d2`、`37cff1d`、`e14441f`） |
| 采购合同 | 从出口合同生成 → 已提交 → 通过/驳回 | 无撤回/作废/关闭 |
| 采购询价 | 草稿 → 报价收集 | 无关闭/作废 |
| 开票通知 | 草稿 → 已发送 → 已收票 | 无编辑/作废 |
| 跟单计划/节点 | 自动生成；由样品/QC/入库/出库回写 | 无手工完成/延期/作废 |
| QC 查验 | 待查验 → 已完成/已取消/问题处理 → 返检 | 无审批；问题关闭后不可重开 |
| 样品申请 | 草稿 → 已发送 → 进行中 → 已完成 | 无编辑/取消/关闭；不可回退，`completed` 仅客户确认阶段且已进行中（`b2541c1`） |
| 样品登记 | 登记 → 库存变动 | 无编辑/删除/冲销；手工发货流水按寄样单号去重（`8aea041`） |
| 寄样 | 草稿 → 已提交 → 已审批 → 运输状态更新；已提交可驳回（→已驳回）或撤回（→草稿）；已驳回编辑自动回草稿，重新提交清空原因 | 已进入 `shipped` 或产生 `delivered` 库存流水后不可驳回/撤回；`rejected` 不可更新物流（`caa2f9e`、`4680f7e`、`bd29695`） |
| 入库计划 | 生成 → 排期 | 无手工创建/编辑/作废 |
| 入库单 | 生成 → 已提交 → 已审批 → 库存入账 | 无作废/撤回 |
| 出库计划 | 生成 → 排期 | 无手工创建/编辑/作废；物料出库类型无入口 |
| 出库单 | 生成 → 已提交 → 已审批 → 库存扣减 | 无作废/撤回 |
| 财务单据 | 创建 → 认领/分配/审批/支付 | 无编辑/作废/冲销；结算不可解锁 |
| 人工待办 | 创建 | 无完成/关闭/改派 |
| 日程 | 创建、删除 | 无编辑 |
| 通知 | 种子数据、标记已读 | 业务动作不产生通知 |

**共性问题**：状态枚举比状态动作多。枚举里定义了 `rejected`/`cancelled`，但多数模块没有对应接口。结果是“看起来支持，实际不可达”，这比没有状态更危险。

### 6.2 近期做（影响核心业务闭环）

1. 补齐出口合同、出货、入库、出库的驳回/撤回/作废；统一状态动作与权限。

5. 明确 UI 组件库决策（继续 Semi 或移除 Semi）。

### 6.3 投产前必须做

1. Alembic 基线 + 迁移版本化 + CI 漂移检查。
2. 明确数据库选型：继续 SQLite 单机，还是切 PostgreSQL；同步修正 `docs/03` 和部署说明。
3. 多币种财务口径确认：是否需要汇率表/折算规则；当前总额直接跨币种相加不可用于对外报表。
4. 备份/恢复与升级流程验证（SQLite 文件 + 本地附件目录）。

### 6.4 暂不建议做

- 不要为了“结构整齐”重写客户/供应商 CRUD。
- 不要现在大拆全局 CSS。
- 不要引入通用工作流引擎：当前只有 2 类合同审批，规则简单，专用状态机更合适。
- 不要为了追求“文档全覆盖”补写大量理论文档；优先修正会误导决策的架构/状态文档。
