## P1：资金一致性

### AUD-004 收款并发分摊突破余额

历史测试对象为专门创建的水单 `BR-MWYV53`，金额 100 USD。认领后同时提交两笔各 60 USD 的合同分摊，两个响应均为 201。

- 预期：最多一笔成功；累计分摊不得超过 100。
- 实际：数据库有两条 60 的分摊，合计 120；页面汇总未分摊为 -20，行内未分摊又被截成 0，呈现出相互矛盾的口径。
- 影响：可产生超额冲销和错误应收余额。接口顺序超额校验有效，但无法保证并发一致性。
- 源码：`receipts/services.py:138` 先读取余额、在 `:147` 校验，之后才进入工作单元写分摊；工作单元只提交/回滚，并没有提供余额占用的原子条件。`receipts/repositories.py:443` 将行内负剩余截成 0。
- 建议：以数据库支持的原子条件/版本检查维护余额约束，并为重复业务请求提供明确的一致性规则；不能只依赖前端 loading 或将负数显示为 0。具体方案需匹配当前 SQLite 行为。

证据：[数据库聚合](checks/full-audit-2026-11-12/db-money-evidence.json)、[历史请求返回](checks/full-audit-2026-11-12/receipt-concurrency.json)、[之后的水单结果](checks/full-audit-2026-11-12/receipt-after-concurrency.json)、[收款页面](checks/full-audit-2026-11-12/pages/28-_finance_receipts.png)。本报告不附可直接重跑的并发写入脚本。

### AUD-005 付款并发审批突破发票余额

历史测试发票 `QA261112-INV01` 总额 100 RMB，两张付款申请各 60 RMB，由指定测试审批角色同时审批，两个响应均为 200。

- 预期：累计付款不得超过发票金额。
- 实际：发票已付 120，有两条各 60 的付款分摊；状态为已付清，未付显示 0。
- 影响：会形成超额付款账务；“已付清”掩盖了已超付的事实。这里是本地账务记录，不能把响应成功解释为已执行真实银行转账。
- 源码：`payments/services.py:187` 的审批流程在进入工作单元前读取发票并校验余额，审批及分摊写入没有把余额条件作为同一原子操作的前提。仓库映射也将负未付截成 0。
- 建议：将审批状态、可付款余额和分摊创建纳入同一一致性保护，核验重复审批/多申请竞争同一发票的行为。

证据：[数据库聚合](checks/full-audit-2026-11-12/db-money-evidence.json)、[历史审批结果](checks/full-audit-2026-11-12/payment-concurrency.json)、[发票及两条付款明细](checks/full-audit-2026-11-12/invoices-after-concurrency.json)。未在安全边界切换后重跑。

## P2：校验、查询、导航与导出

### AUD-001 纯空白商品编码

历史请求将 `code` 设为三个空格，其余字段有效，返回 201；数据库确认 `length(code)=3`、`trim(code)=''`。前端正常录入会 trim 并阻止空值，但服务端 `min_length=1` 不排除空白，创建服务直接使用原值。

建议：在服务端规范化并拒绝空白必填文本，且按规范化后的业务编码检查唯一性。不要仅增加前端判断。证据见 [负向请求结果](checks/full-audit-2026-11-12/negative-checks.json) 和数据库聚合文件。

### AUD-002 QC 自动建任务文案与行为不符

测试采购合同 `PC-HR36RU` 已指定 QC 专员并审批通过；之后跟单计划、入库计划各生成一条，QC 列表仍为 0，直到手动创建任务。采购审批服务只调用采购进度回写、跟单与入库计划创建，没有在该分支创建 QC 任务。

页面却写“采购合同审批后会自动生成 QC 任务”。用户可能因此等待一个不会出现的任务。应明确选择实际要支持的行为，再统一文案和流程；本轮不擅自新增自动业务动作。

证据：[审批后 QC 空页](checks/full-audit-2026-11-12/qc-after-approval.png)、`purchase/contracts/services.py:312` 之后的审批分支。

### AUD-006 编号/名称输入被当成 UUID

这些页面使用普通 Input，提示可以输入业务编号或名称，最终直接将文本发到 `supplier_id` 或 `customer_id`，后端按外键等号匹配。

| 查询位置 | 内部 UUID 查询 | 页面显示的业务编号查询 |
| --- | --- | --- |
| 采购合同 supplier_id | 1 条 | `QA261112-S01` → 0 条 |
| 入库计划 supplier_id | 1 条 | `QA261112-S01` → 0 条 |
| 供应商发票 supplier_id | 1 条 | `QA261112-S01` → 0 条 |
| 收款 customer_id | 1 条 | `QA261112-C01` → 0 条 |

上述 8 次请求均为只读 GET。客户选择器已修复的是“水单录入弹窗”；列表筛选仍是另一条未完成的链路。

建议：使用业务实体搜索选择器，将用户看到的编号/名称解析成 UUID；或者为编号/名称提供明确的查询参数，不能混用外键参数。关键位置：`usePurchaseContractsList.ts:96`、`PurchaseContractListPanel.tsx`、`InboundPlansPage.tsx`、`ReceiptsView.tsx`、付款筛选模型及对应 repository 外键条件。

证据：[只读对照](checks/full-audit-2026-11-12/readonly-filter-checks.json)。其他同形输入是源码影响面，未逐一发送对照请求，不算额外确认实例。

### AUD-007 合法详情链接被列表分页误判

离线模拟当前第一页有记录、总数 51、目标详情是第 51 条：商品、采购合同、出口合同三个 hook 都调用跳转返回列表，而没有独立取目标详情。

原因是把“当前页里没有这个 ID”当成“该详情不存在”。刷新详情、分享详情链接、列表筛选变化或任务入口跳转都可能受影响。

建议：详情按 ID 独立加载；只有详情接口确认不存在或无权限时才显示相应状态，不以分页列表是否包含 ID 决定。已模拟确认：`useProductsPage.ts:137`、`usePurchaseContractsList.ts:72`、`useExportContractsList.ts:64`。其他多个列表存在同形判断，列入后续覆盖，不直接视为全部实测。

证据：[离线结果](checks/full-audit-2026-11-12/safe-mock-results.json)，3 个深链用例。没有在容器中创建 51 条记录。

### AUD-008 旧查询响应覆盖新结果

离线让查询 older 先发出、newer 后发出，先返回 newer 的结果，再返回 older：最终界面模型留下的是 older 的过期结果，输入条件仍是 newer。

源码 `usePurchaseContractsList.ts:78` 的列表请求没有请求序号或取消保护，返回后直接更新列表、总数、摘要和选中项。其他列表是否同样受影响需分别验证。

建议：只接纳当前有效查询的结果，并同时保护 loading、汇总和选中状态。证据是内存 Promise 模拟，没有并发访问真实接口。

### AUD-009 CSV 文本未防公式解释

离线模拟商品名称为无害文本 `=1+1`，调用真实导出服务；解析导出的 CSV 后，该文本单元格仍以 `=` 开头。没有真实打开 Excel 或执行任何公式。

源码 `products/services.py:297` 把用户文本直接写入 `csv.writer`。CSV 的引号/逗号转义不能保证电子表格将公式前缀按普通文本处理，因此存在公式注入风险。报价、合同、样品、报表等也有直接 CSV 写文本的代码，但本轮只对商品导出做了离线复现。

建议：对可控文本单元格采用统一的安全导出策略；区分文本和真实数值列，避免破坏正常金额。增加公式前缀、制表符、换行、引号等纯内存样例。

证据：[离线导出结果](checks/full-audit-2026-11-12/safe-export-tests.log)、[只读模拟代码](checks/full-audit-2026-11-12/readonly-repros/exports.repro.py)。

### AUD-010 “导出全部”被分页限制

`export_products` 明确调用 `list_products(limit=10000)`，但 GET 分页中间件对所有 GET 设置默认 limit=50；repository 的 `resolve_limit` 优先使用该上下文。因此导出也会受默认页长影响。

离线使用真实分页上下文和遵循同一 resolver 的模拟仓库：51 条只导出 50 条；不带 HTTP 上下文时，10001 条只导出 10000 条。返回结果没有截断提示。

建议：导出拥有独立于页面查询的批量读取契约，分页中间件按路由语义限定作用范围；若必须限制总量，应明确告知而不是把截断结果称为全部。涉及 `api/pagination.py:57`、`core/pagination.py:26`、`products/repositories.py:466`、`products/services.py:290`。

证据同离线导出日志。没有向当前库批量造数或实际导出大文件。

- 未完成 QC 时正式入库被拒绝，完成后可入库；测试库存流水与数量为入库100、盘点减少21、出库20，余额59。
- 样品超量寄出、重复寄样审批、未完成打样转登记均被拒绝；客户确认完成后可转样品登记。
- 报价驳回后需编辑回草稿再提交，随后可审批并转合同。
- 未审批报销付款、重复报销付款、退税超过剩余额度、未核销先退税、重复结算、口岸导入条数不匹配均被拒绝。
- 水单选择客户后，客户名称只读带出，空付款人自动填入；这是此前有测试客户后实测的结果。

这些正常链路中涉及业务写入的步骤均发生在用户要求降低风险之前；后续只核对现有证据。
